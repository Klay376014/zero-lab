## Context

Lynx 的雙線程架構把事件與處理常式分在兩邊：事件在主線程發生，Vue 的處理常式在背景線程執行，狀態改變後才把 ops 送回主線程重繪。這個往返的延遲是架構固有的，不是本專案的實作缺陷。

本專案目前完全沒有遮掩它。`src/App.css` 沒有任何按壓態樣式，平台也沒有 `:active` 偽類可用，所以在往返完成之前畫面上沒有任何反應。查詢列的型別鈕是最壞的情況：那一下要等 208 個物種重新篩選、208 張卡重新 diff 完才有畫面改變。

這是本專案第一次使用主線程腳本，所以它同時是一個功能與一次平台探勘。以下三件事在寫這份設計時已經查證過，不是假設：

1. **裝的 `vue-lynx` 0.4.0 確實實作了主線程腳本，不是只有文件寫。** 背景線程的 `patchProp` 攔截 `main-thread-` 前綴的屬性，其中 `ref` 走 `SET_MT_REF` op、其餘經事件名解析後走 `SET_WORKLET_EVENT` op；主線程的 ops 套用器消費這兩個 op。執行期匯出 `useMainThreadRef`、`runOnMainThread`、`runOnBackground`。**這一點特地查了**，因為 `design/HANDOFF.md` §12.13 記過一次官方 guide 描述的 `<list>` 行為在出貨程式碼裡根本不存在。
2. **事件屬性的拼法是 `main-thread-bind` 直接接事件名**，中間沒有分隔符 —— 屬性名去掉 `main-thread-` 前綴之後，用的是與一般事件同一套解析（`bind` 開頭者視為 bindEvent），所以正確寫法是 `main-thread-bindtouchstart`。
3. **背景線程的樣式更新是整份取代，不是逐屬性合併。** 這一條決定了本設計一半的內容，見〈主線程寫的樣式會被背景線程的重繪整份抹掉〉。

## Goals / Non-Goals

**Goals:**

- 手指按下控制項的當下，主線程就畫出按壓態，不等背景線程。
- 按壓態在任何情況下都不殘留：正常放開、手勢被取消、按壓中途背景線程重繪，三種路徑都要回到未按壓的樣子。
- 既有的 `@tap` 與所有狀態邏輯零改動。主線程只加一層視覺，不接管任何行為。
- 把這次量到的平台事實寫進 `design/HANDOFF.md`，讓下一次用主線程腳本的人不必重新探勘。

**Non-Goals:**

- 不綁 208 張卡與詳情面板的遮罩（理由見 proposal 的 Non-Goals）。
- 不用不透明度或換色表示按壓（同上）。
- 不改善搜尋輸入的延遲 —— 那是背景線程的純計算，主線程腳本對它無效。
- 不引入 `useMainThreadRef`：本次每個回饋都只作用在事件自己的 `currentTarget` 上。
- 不加無障礙屬性。

## Decisions

### 按壓態是位移一個像素，不是換色也不是改不透明度

按下時 `transform: translateY(1px)`，放開時清掉。

替代方案與否決理由：

| 方案 | 為什麼不用 |
|---|---|
| 降低不透明度 | `retro-theme` spec 與 `ROADMAP.md` C 節明文禁止遮罩以外的任何半透明表面 —— 會合成出四階灰以外的顏色，遮罩是唯一例外而不是前例 |
| 換成 `--accent` 或 `--surface2` | `--accent` 正是「選中」態的顏色，未選中的鈕按下去會瞬間看起來像已經選中；POCKET 的四階灰契約下也沒有第五個色可以借 |
| 加陰影表現凹陷 | 平台忽略 `inset` 陰影（§12.3），而 `pnpm run check` 的第二項檢查就在擋這個屬性 |

位移還有兩個附帶好處：對選中與未選中兩種底色的效果完全一致，所以不必為兩種狀態各寫一條規則（§12.15 記過「缺一條 `On` 規則」這類靜默失效）；而且完全不碰顏色，所以 `check-contrast.mjs` 的量測面不受影響，不需要教它任何新東西。

`transform: translateY` 在 iOS 已由 §12.14 的探針確立可用。

### 三個觸控事件都綁，不是兩個

`touchstart` 上按壓態，`touchend` 與 `touchcancel` 都要清掉。

只綁 `touchend` 會留下一個實際會遇到的壞狀態：招式表的排序鈕與形態鈕都在詳情面板的捲動容器內，手指按在鈕上然後移動去捲動，這一下不會產生 `touchend`。少綁 `touchcancel` 的結果是一顆永遠凹著的鈕，而且它不會自己好 —— 除非那顆鈕剛好被背景線程重繪。

### 主線程寫的樣式會被背景線程的重繪整份抹掉

**已查證的事實**：背景線程的 `style` prop 更新推出 `SET_STYLE` op，主線程收到後呼叫 `__SetInlineStyles(el, value)` —— 傳的是整個樣式物件，**整份取代**，不是逐屬性合併。所以背景線程每一次觸及 `style` 綁定的重繪，都會抹掉主線程用 `setStyleProperty` 寫進去的東西。

這對兩類控制項的意義相反，設計要分開講：

**沒有 `:style` 綁定的控制項**（模式鈕、語系鈕、重置鈕、世代鈕、排序鈕、形態鈕、招式排序鈕、屬修鈕、關閉鈕）—— 背景線程只推 `SET_CLASS`，不碰行內樣式。主線程寫的位移會活著，**因此必須由主線程自己清掉**。這是上一項決定裡 `touchend` 與 `touchcancel` 存在的理由。

**有 `:style` 綁定的型別鈕** —— 型別鈕的背景色是行內綁定的。按下去之後背景線程處理該次點擊、重新求值那個樣式物件、推出 `SET_STYLE`，位移就在那一刻被抹掉。

**這個結果是可接受的，不需要繞開**：按壓態被抹掉的時間點，正好是真正的狀態改變落到畫面上的時間點 —— 也就是按壓態不再需要存在的時間點。要避免的失敗是「卡住」，而整份取代的語意保證了卡不住。所以本設計**不**為型別鈕改寫背景色的上法，也不試圖讓主線程與背景線程協調同一份樣式物件。

**這條要寫進 `design/HANDOFF.md`**：它是通則，不只關於按壓回饋 —— 任何「主線程寫樣式、背景線程也綁 `:style`」的組合都適用。

### 先跑探針，再寫任何實作

主線程腳本的失敗形態正是 §12.17 記的第三類坑：宣告寫得下去、不報錯、行為沒發生。屬性名拼錯、`'main thread'` 指示詞沒被建置期的轉換認出、或轉換沒有涵蓋到某個檔案，三種失敗在畫面上長得一模一樣，而且與「平台不支援」也長得一模一樣。

所以第一項工作是一個**無條件**的探針，照 §12.14 建立 `@keyframes` 時的做法：按下必定改變某個一眼可辨的東西，且不依賴任何其他決定是否正確。探針過了才知道後面量到的是效果問題而不是綁定問題。

探針同時要回答一個本設計無法從程式碼推定的問題，見下。

### 主線程函式放哪裡，由探針決定

官方文件的每個範例都把 `'main thread'` 函式定義在元件內部。**本設計偏好把它們集中在一個模組**（依 Impact 所列的互動模組），讓五個元件只負責綁定、不各自複製同一段邏輯。

但建置期的 worklet 轉換是否涵蓋元件以外的獨立模組，從裝的套件讀不出來 —— 這要實測。所以：

- 探針的第二個問題就是「從獨立模組匯入的主線程函式會不會生效」。
- **若不生效**，退路是把函式定義在各元件的 `<script setup>` 內，並把共用的常數以 `with { runtime: 'shared' }` 匯入。這條退路會讓同一段三行邏輯出現在五個元件裡，是可接受的代價 —— 但**不要在探針回答之前先照退路寫**，那會白白付出重複的成本。

### 範圍以「已經有 `@tap` 的控制項」為界

37 個控制項，分佈如下。卡片與遮罩排除，理由在 proposal。

| 元件 | 控制項 | 數量 |
|---|---|---|
| 應用外殼 | 模式鈕、語系鈕 | 2 |
| 查詢列 | 重置鈕、型別鈕、世代鈕、排序鈕 | 1 + 18 + 9 + 2 |
| 形態切換器 | 形態鈕（每個物種不同，最多視形態數而定） | 視資料 |
| 招式表 | 三顆排序鈕、屬修鈕 | 4 |
| 詳情面板 | 關閉鈕 | 1 |

## Implementation Contract

**Behavior** —— 使用者按下上表任一控制項時，該控制項在手指接觸的同一格畫面內向下位移 1px，且這個位移不等待背景線程。放開手指、或手勢被系統取消、或背景線程在按壓期間重繪了該元素，三者任一發生後，控制項都回到未位移的位置。控制項原本的行為（選中、篩選、排序、關閉面板）完全不變。

**Interface** —— 對外的形狀是三個綁定在控制項元素上的屬性：`main-thread-bindtouchstart`、`main-thread-bindtouchend`、`main-thread-bindtouchcancel`，各自接一個標了 `'main thread'` 指示詞的函式。函式只讀 `event.currentTarget` 並呼叫其 `setStyleProperty`，不讀取也不寫入任何背景線程的狀態，不呼叫 `runOnBackground`。清除位移的方式是把 `transform` 設為空字串。

**Failure modes** —— 綁定失敗是靜默的：屬性名錯誤或轉換未涵蓋都不會報錯，畫面上等同於功能不存在。這是探針必須先於實作的唯一理由。型別鈕的按壓態被背景線程的 `SET_STYLE` 提早抹掉是**預期行為**，不是缺陷，不需要修。

**Acceptance criteria**

1. `pnpm run check` 與 `npm exec tsc -- --noEmit -p src/tsconfig.json` 皆通過。位移不涉及顏色，所以對比檢查的組合數應與本次改動前一致 —— 若數字變了，表示有人順手動了顏色，該退回。
2. 探針在 iOS 實機上確認綁定生效，且確認了獨立模組的匯入是否可用。兩個答案都寫進 `design/HANDOFF.md`。
3. iOS 實機逐項確認：查詢列四類鈕、形態鈕、招式表四顆鈕、關閉鈕按下去都有位移。
4. iOS 實機確認取消路徑：手指按在招式表的排序鈕上、不放開直接往上滑去捲動面板，放開後該鈕**不**停留在位移狀態。這一項是 `touchcancel` 綁定的唯一驗證方式，web 預覽答不了 —— §12.19 已記過 web 預覽跑的是瀏覽器的捲動與手勢實作而不是 native 的手勢鏈。
5. iOS 實機確認卡片與遮罩**沒有**按壓態（本次刻意排除的範圍確實被排除）。

**Scope boundaries** —— 在範圍內：上表 37 個控制項的按壓回饋、其樣式規則、主線程函式、以及 `design/HANDOFF.md` 的新增一節。在範圍外：卡片與遮罩、無障礙屬性、搜尋輸入的延遲、任何顏色或既有樣式規則的改動、任何 `@tap` 處理常式與狀態模組的改動。

## Risks / Trade-offs

- **[綁定靜默失效，看起來像平台不支援]** → 探針先於實作，且探針的判別方式是「無條件、必定改變一眼可辨的東西」，而不是看樣式表或看程式碼。這是 §12.14 與 §12.17 兩次都用過的做法。
- **[獨立模組的主線程函式可能不被建置期轉換涵蓋]** → 探針的第二個問題就是它，退路（定義在各元件內）已寫在決定裡。退路的代價是重複三行邏輯五次，不是重做設計。
- **[37 個控制項各加三個事件，首屏多出約 111 個 `SET_WORKLET_EVENT` op]** → 相對於卡片路徑的 624 個小一個量級，而且查詢列的控制項數量是固定的、不隨資料集成長。這正是排除 208 張卡的理由 —— 成本與收益的比例在卡片上是反的。
- **[1px 的位移在高密度螢幕上可能太細微而察覺不到]** → 這是實機驗收才答得出來的，不是設計期能定的。若確認太細微，調整的是 `App.css` 裡的單一數值，不動任何主線程程式碼。位移量刻意不寫進主線程函式，就是為了讓這次調整不必再碰跨線程的部分。
- **[本專案第一次使用主線程腳本，等於引入一個新的執行環境]** → 範圍刻意限制在「只讀 `currentTarget`、只寫一個樣式屬性、不呼叫 `runOnBackground`、不用 `useMainThreadRef`」。這是這個機制最小的可用子集，讓第一次使用不必同時承擔跨線程狀態同步的風險。

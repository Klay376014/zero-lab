## Context

`add-moves-tab`（2026-08-11 archive）把 21 種招式 flag 的編號寫進了 `Move.fl`：425 筆招式帶至少一個，71 筆省略該鍵。那一批刻意不顯示任何 flag，理由寫在它的 design.md，而顯示範圍的取捨留給後續 change。

那次取捨已於 2026-08-11 討論完成，結論寫在 `ROADMAP.md` A11：判準、四個排除、17 個中英簡稱、每筆最多 4 顆晶片的分佈、以及三個已查過不成立的風險。本 change 交付那個結論。

三個當前狀態上的限制：

- **編號到 identifier 的對照表不在 repo 裡。** `design/pipeline/fetch_sources.sh` 只抓 `move_flag_map.csv`（哪個招式帶哪些編號），沒抓 `move_flags.csv`（編號叫什麼）。所以資料集裡的 `4` 與 `7` 目前是不透明的數字
- **簡稱上游完全不存在。** `move_flag_prose.csv` 的 zh-Hant 為 0 列，中英兩側都得自己寫。而 `dex-data` 的 provenance 要求禁止在資料集裡手寫內容，所以簡稱不得進資料集
- **`fl` 目前唯一的防護是 `tests/dex-data.test.ts`。** 介面不讀它，所以四項 check 與 `vue-tsc` 都看不到它。交付之後介面會讀，但 `vue-tsc` 不檢查 Lynx 元素屬性，所以測試仍是主要防護

## Goals / Non-Goals

**Goals:**

- 招式詳情以既有屬性清單的一列顯示 17 種 flag 的簡稱，中英各一組，每筆招式最多 4 顆
- 排除四種 flag，且排除的表達方式不需要一份額外的清單來維護
- 零晶片的招式不渲染那一列，且不對「上游沒填」與「被濾光」做任何斷言
- pipeline 產出編號到 identifier 的對照，讓上游改名可被測試抓到、改編號不影響簡稱
- 改寫 `move-detail` 與 `dex-data` 兩份 spec 裡已經不成立的敘述

**Non-Goals:**

- **不重新討論「舞蹈」這個簡稱。** A11 定案是「舞蹈」／`Dance`，中文側曾寫過「舞者」並已被否決（招式不是舞者）。要改回是一個獨立決定
- **不分組、不用樣式區分語意方向。** 17 個名詞裡「重力」「守住」「反彈」的方向與其餘正向標籤相反，純名詞承載不了方向，這個代價已定案接受
- **不顯示機制說明。** `ROADMAP.md` A11 表格第四欄那 21 條句子描述的是本傳行為，而本資料集 496 招裡 401 招的威力／命中／PP 被 Champions 重調過
- **不在招式表或招式索引顯示 flag。** 只有招式詳情這一層
- **不處理無障礙屬性。** 那是 `ROADMAP.md` B 節的整體主題，不在這一批夾帶
- **不新增模組。** 簡稱查詢是 `src/data/i18n.ts` 的一個函式
- **不沿用 `.Chip` 系列，也不改動它。** 見「簡稱是顯示用標記，不是控制項」；`QueryBar` 的晶片行為不在這一批的範圍內

## Decisions

### 判準是「名詞能否描述招式本身的性質」，不是覆蓋率

`add-moves-tab` 的 design.md 當初寫的理由是「`protect` 與 `mirror` 各覆蓋近七成，全顯示等於掛兩顆沒有資訊量的標籤」。**這條規則取代它** —— 按覆蓋率 `protect`（340 筆）該被砍，而定案是留下它。

規則：名詞能描述招式本身的性質就留；只能描述「與某個機制的關係」而那機制不在這個資料集裡就砍。

依此排除四種：`mirror`（鸚鵡學舌不在 496 招裡）、`snatch`（搶奪不在）、`non-sky-battle`（空中戰鬥形式不存在）、`distance`（三打不存在）。

`heal` 與 `dance` **保留**，儘管回復封鎖不在 496 招裡、Dancer 不在 200 個特性裡 —— 因為「回復」說的是這招會回復、「舞蹈」說的是這是舞系招式，都不依賴那個機制存在。`protect` 保留，因為看穿與守住都在 496 招裡，關係是真的。

**替代方案：按覆蓋率門檻砍。** 會砍掉 `protect` 而留下 `mirror` —— 恰好留下機制不存在的那個。而門檻本身是品味，寫不進 spec 的 SHALL。

### 編號到 identifier 到簡稱的兩段式綁定

pipeline 產出編號到 identifier 的對照（衍生資料），`src/data/i18n.ts` 以 identifier 字串為鍵掛簡稱。

**替代方案：把編號直接對到簡稱，寫死在字串表。** 少一跳，但上游重編號會靜默錯標，而依 Context 第三點，沒有任何 check 會抓到。經過 identifier 這一跳之後，上游改名讓簡稱查不到（可測），改編號不影響任何簡稱。

**這一跳不是為了分層**，所以不再包第二層：`i18n.ts` 一個依 identifier 取簡稱的函式就是全部，多一個模組是 pass-through。

### 排除四種 flag 的方式是不給它們簡稱

資料集的對照表收錄**全部 21 種** identifier，字串表只給 17 種簡稱。介面遇到查不到簡稱的 flag 就跳過。

於是「顯示哪幾種」完全由字串表決定，**沒有第二份排除清單要跟它保持同步**。資料集不編碼顯示決定，這也與「簡稱歸字串表」同一個道理。

**替代方案：pipeline 只輸出 17 種。** 會把 UI 決定寫進資料集，且日後要改顯示範圍就得重跑 pipeline。

### 零晶片時整個區段不渲染

不寫「無」、不給計數、不留空的列標籤。71 筆上游沒填與 42 筆被濾光因此在畫面上無法分辨。

**這是刻意的**：只顯示正例、從不宣告缺席，就不對那 71 筆做資料不支持的斷言。寫了「無」或給一個 `0`，正好是 `move-detail` 現行 spec 拒絕的那句斷言 —— 那條 Requirement 的理由要被保留，不是被推翻。

### 簡稱是屬性清單的一列，不是說明之後的獨立區段

`src/components/SpeciesDetail.vue` 已經解過「值是一組多值、不可點的標記」這個問題：**屬性**不是自己一個區段，而是 `DetailAttrs` 裡的一列 —— 標籤用 `.DetailAttrKey`，值欄放會換行的 `.DetailAttrTypes`，標記用 `.TypePill`。flag 簡稱是同一種東西，所以走同一條路：既有清單（屬性／傷害類別／威力／命中／PP）的第六列，排在 PP 之後。

**替代方案：說明文字之後、學習者入口之前的獨立區段（原本的計畫）。** 三個問題：面板讀成「資料 → 散文 → 資料 → 動作」的鋸齒；為了一件既有清單已能承載的東西新增一個標題與第四塊；而且零晶片時消失的是一整個帶標題的區塊而不是一列，113 筆招式的版面落差因此大得多。

**排在 PP 之後而不插在數字之間**：這一列高度會變（0 到 2 行），插在威力／命中／PP 之間會打斷那三個數字的縱向掃視。

### 簡稱是顯示用標記，不是控制項

`.Chip` 系列**不能用**：它有 `.ChipOn`，在 `QueryBar` 裡帶三個主線程觸控綁定，是控制項的視覺語言。flag 簡稱不可點，用控制項的樣式會招來沒有反應的點擊。

這個面板裡顯示用的角色是 `.TypePill`（無 `On` 態、無觸控綁定），但**不直接沿用它**：它的 3px 框與字符槽是為「屬性」這個身分設計的，而屬性的層級高於 flag。所以要一個比它安靜一級的兄弟 —— 1px 框、無字符槽、無狀態。

換行沿用既有原語 `.DetailAttrTypes`（值欄裡一組會換行的標記），所以橫向捲動的問題根本不出現，也不需要新的捲動決定。

### `Flags` 這個列標籤是量出來的，不是挑好看的

`.MoveDetailAttrKey` 的 88px 是為 `ACCURACY`（81.5px）量的，該規則的註解記載 62px 欄曾讓 `ACCURACY` 斷成 `ACCURA / CY` 並把列基線拉歪。新標籤必須量。

以 `src/assets/fonts/Silkscreen-Regular.ttf` 自己的 advance width 在 12px 加 1px tracking 下計算（此方法已重現該註解裡 `ACCURACY` 81.5、`DESCRIPTION` 99.5、`DAMAGE` 60.0、`Roster` 57.0 四個既有數字，所以可信）：

| 候選 | 寬度 | 88px 欄 |
|---|---|---|
| `Flags` | 47.0 | 剩 41.0 —— **採用** |
| `Traits` | 52.5 | 剩 35.5 |
| `Effects` | 62.5 | 剩 25.5 |
| `Properties` | 91.0 | **溢出 3.0，會斷行並拉歪基線 —— 棄用** |

中文側是「性質」，兩個字沒有寬度問題。**中英不對譯**（英文用上游的字 `Flags`，中文用白話的「性質」），理由與 `authentic`／`reflectable` 同列，一併寫進 change。`Effects` 另有語意問題：flag 不是效果。

### 改寫 move-detail 的 flag Requirement 而非新增一條

`openspec/specs/move-detail/spec.md` 現有一條 "Move flags are carried by the data layer and are not displayed"。新增一條要求顯示會讓 spec 自相矛盾，所以**改寫這一條**，並保留它「不能對 71 筆做斷言」的理由（那個理由仍然成立，只是現在由「不宣告缺席」來滿足，不再由「完全不顯示」來滿足）。

`dex-data` spec 的 Purpose 第三段寫著 flag「stored and read by nothing」，同時失效，一併改。

## Implementation Contract

**Behavior**：招式詳情的屬性清單多一列「性質」，排在 PP 之後，值是該招式帶有的 flag 簡稱標記。中文語系顯示中文簡稱，英文語系顯示英文簡稱，切換語系時整列重述。該招式沒有任何可顯示的 flag 時，**這一列的所有元素都不建立** —— 沒有標籤、沒有容器、沒有佔位文字，清單少一列。

**晶片順序沿用 `fl` 既有的編號升冪**，不另排序。`dex-data` 已經要求 `fl` 升冪，所以照順序取就是穩定的。這個順序**穩定但不具意義**（編號是上游的流水號）—— 選它的理由正是不必再引入一個排序規則；不要改成依簡稱筆畫、依覆蓋數或依語系排序。

**Interface / data shape**：

- 資料集新增一個頂層鍵，內容是編號到 identifier 的對照，收錄全部 21 種。鍵為編號的字串形式，值為上游 identifier（例如 `protect`、`non-sky-battle`）。`src/data/dex.ts` 為它加型別
- `src/data/i18n.ts` 新增一個依 flag 編號與語系取簡稱的函式。查不到時回傳空值而非拋錯，供介面跳過
- 字串表收錄 17 種 identifier 的簡稱，中英各一組。四種被排除的 identifier 在兩個語系都**沒有**條目
- 17 組簡稱的值以 `ROADMAP.md` A11 表格的「簡稱」與「英文」兩欄為準

**Failure modes**：

- 查不到簡稱的 flag（四種被排除者，或上游新增的第 22 種）→ 介面**靜默跳過**該顆晶片。**畫面安靜是刻意的**：一個沒人寫過簡稱的 flag 不該憑 identifier 出現在畫面上
- 上游新增 flag 種類 → 兩道防護，畫面仍然安靜：某招式的 `fl` 出現對照表沒有的編號時，**載入期不變式拋錯**（`dex-data` 既有的整體性斷言那一類）；對照表筆數（21）的斷言則在 `tests/dex-data.test.ts` 失敗。前者處理「資料集自我矛盾」，後者處理「上游擴充但對照表沒跟上」，兩者不是同一件事
- 上游更名 identifier → 對照表與 `fl` 仍然一致，載入期不拋錯；該 flag 的簡稱查不到，晶片消失，由字串表的簡稱覆蓋斷言抓到。**這正是選擇以 identifier 為鍵的目的** —— 若以編號為鍵，這個情形會靜默錯標而非靜默消失

**Acceptance criteria**：

- `pnpm test` 通過，且新增三條斷言：（一）沒有任何招式帶著簡稱與自己中文名同字的 flag；（二）恰好 17 種 identifier 在兩個語系都有簡稱，四種被排除者兩語系都沒有；（三）對照表收錄 21 種，且每個出現在任一招式 `fl` 裡的編號都在表內
- `pnpm test` 既有的 flag 斷言不變（425／71／21 種／單筆最多 6／升冪／無空陣列）—— 這一批不改資料集的 `fl` 內容
- `pnpm run check` 與 `pnpm run typecheck` 通過
- 重跑 pipeline 後 `src/data/dex.json` 與 `design/champions-dex.json` 除了新增那個頂層鍵之外沒有差異
- **實機驗收**（`vue-tsc` 不檢查 Lynx 元素屬性，標記是新的元素樹）：帶 4 顆標記的招式在值欄內換行且不溢出；`Flags` 標籤在 88px 欄內不換行；**標籤與標記垂直互相置中**（見下方 Risks 的實機發現 —— 這一列不能用基線對齊）；零晶片的招式看不出少了一列；招式詳情仍然只有一個捲動容器
- 依 `ROADMAP.md` 維護方式，A11 從 A 節移除

**Scope boundaries**：

- **In scope**：pipeline 新增 `move_flags.csv` 來源與對照表輸出、資料集型別、字串表 17 組簡稱與 `mdFlags` 列標籤與查詢函式、招式詳情的「性質」列與顯示用標記樣式、兩條新測試、兩份 spec 的改寫、`ROADMAP.md` A11 移除
- **Out of scope**：Non-Goals 全部各項；`fl` 本身的內容（不重抓 `move_flag_map.csv`）；`learnset-table` 與 `move-index` 的任何改動

## Risks / Trade-offs

- **純名詞承載不了語意方向** →「重力」意思是重力場下不可使用、「守住」意思是會被守住擋掉，方向與其餘正向標籤相反。已定案接受：每筆最多 4 顆，分組買不到什麼，而分組會讓已無晶片的 113 筆多出「有一組空著」的狀態
- **簡稱與資料集既有名稱同字** →「最壞情況不會發生」這個原始結論**只跑了中文比對，實作時測試抓到兩件事**。
  中文側成立：`守住`／`蓄力`／`重力` 是招式名、`穿透` 是特性名、`波動` 是六個招式名的組成，但招式「守住」不帶 `protect`、「蓄力」（Stockpile）不帶 `charge`、「重力」只帶已排除的 `non-sky-battle`。
  **（一）英文側有一個自撞，判定接受**：招式 Bite 帶 `bite`，英文詳情讀作 `Flags: … Bite`。Bite 確實是啃咬招式，同義反覆但為真，與「晶片被讀成另一個招式」不同；中文側是 咬住 vs 啃咬，不撞。測試釘住 `['Bite']` 這個確切集合而非空集合 —— 上游沒有機制阻止第二個出現，而第二個可能就不是同義反覆（例如 `charge` 若被加到 Stockpile 上）。
  **（二）`reflectable` 的英文標籤從 `Reflect` 改為 `Rebound`**：`Reflect` 是這 496 招裡一個招式的名字（光牆），而此 flag 的機制是魔法鏡，兩者無關 —— 英文讀者會把標籤當成指向光牆的指標。其餘三個同時是招式名的標籤沒有這個問題，因為它們指的就是那個招式（`Protect` 被守住擋、`Gravity` 重力場下不可用、`Charge` 語意相符）。中文「反彈」不動，中文沒有同名招式
- **71 筆與 42 筆在畫面上無法分辨** → 無法緩解，是「不宣告缺席」的必然結果。可緩解的部分是不做出斷言，而那已經是設計的一部分
- **顯示 flag 等於在一個重調過數值的遊戲上談本傳機制** → 緩解方式是只寫名詞不寫機制說明。名詞是索引標記，不是規則敘述
- **新增元素的繪製成本**（平台按元素計價，約 1.3ms 一個，見 `design/HANDOFF.md` §12.24）→ 每筆最多 4 顆晶片，且招式詳情一次只顯示一筆。與 `window-visible-range` 處理的長序列不同量級
- **實機是唯一能驗晶片版面的地方** → 網頁預覽量到的文字寬度不可信（像素字面不載入），§12 有替代做法。晶片換行必須在裝置上看。**這一條在實機驗收時兌現了**：`align-items: baseline` 對 `<text>` 子元素成立（上方五列都對齊），對**容器**子元素不成立 —— 平台取容器的 baseline 是它的**下外邊距邊緣**，而不是裡面文字的 baseline，所以 `FLAGS` 標籤被標記自己的 `margin-bottom` 往下推。處置：這一列改為 `align-items: center`，標記的上下外邊距對稱（3px + 3px），使一行與兩行的置中都精確。**這是 §12 那個形狀的又一例**（宣告被接受、沒有錯誤、行為就是不發生），值得考慮補進 §12；`SpeciesDetail` 的屬性列結構相同，可能有同樣的偏移，但沒有量過所以沒有動

## Context

移植版的資料集是 pipeline 產物，不是手寫資料。因此「更新到 M-C」這件事的本體是**讓 pipeline 在新的上游輸入下跑得出正確結果**，而不是編輯任何一份輸出。`dex-data` 規格明文禁止手改輸出，且要求同樣的輸入必須逐位元重現同樣的輸出。

現況：`src/data/dex.json` 的 meta 自述 M-B，六項載入期不變式寫在資料層模組裡，八份規格的 Example 表帶著資料集規模的字面值，而 `pnpm test` 會把那些表對真實模組執行。三者必須同時落地。

本次的上游輸入變動已在隔離副本中完整跑過一次（複製 pipeline 到暫存目錄、換上即時抓取的名單頁與分類頁、逐步排除失效後跑完步驟 0 至 7），所以下列數字是量出來的，不是推估的。

### 約束

- 上游只提供 `abilitym` 欄位作為新 MEGA 的特性來源；PokeAPI 對這兩個形態沒有任何特性列。不得自行發明資料。
- pipeline 步驟 0 至 7 只寫入 pipeline 目錄內，步驟 8 才寫出 `design/champions-dex.html`、`design/champions-dex.json` 與 `src/data/dex.json`。這是隔離試跑可行的原因，也是驗證時可以先看 dex3.json 再決定是否產出的原因。
- Node 測試碰不到版面、手勢與字型度量。招式名的欄寬容納屬於裝置驗收。

## Goals / Non-Goals

### Goals

- pipeline 在 M-C 輸入下跑完且每一個既有斷言都仍然成立（更新過期望值之後）
- 資料集的 meta 不再對任何規模計數寫入字面值
- 八份規格的 Example 值與新資料集一致，`pnpm test` 全綠
- `ROADMAP.md` D 節只剩條件尚未成立的項目

### Non-Goals

- 不更動 `press-feedback` 與 `visible-range-window`：其中的 208 是敘述與演算法範例輸入，不是對資料集規模的斷言
- 不收錄席多藍恩（485）與超級席多藍恩：仍是註解列且不在學習表分類中
- 不重抓 PokeAPI CSV 與 52poke 快取
- 不調整任何畫面、樣式或互動行為

## Decisions

### 決策一：「其他形態」區段以「下一個第二層標題」作結，而非具名的下一節

上游刪除了 `==Untransferable Pokémon==`，而解析器用它當作「其他形態」區段的結束樣式。比對不到時 `section()` 回傳空字串，該區段的 87 筆形態會安靜消失 —— 這是本次唯一一個不拋錯的失效，正是專案反覆遇到的那一類。

改為比對下一個第二層標題。**採此法而非改指 `\n==Trivia==`**：後者只是把同一個脆弱性換一個名字綁上去，上游再插一節就再壞一次；前者對「其他形態之後是什麼」不作假設。

### 決策二：meta 的 MEGA 與地區形態計數改為計算值

這兩項目前是寫死的 78／16，而同一個 meta 裡其餘十項都是算出來的。規格要求 meta 的四項規模計數各自對應一項載入期不變式所斷言的計數 —— 字面值讓同一件事有兩個獨立來源，只有在兩邊剛好相等時看起來是對的。M-C 之下實際值是 81／17，若只把字面值改成新數字，下一次輪替會再出現同樣的分歧。

**採「計算」而非「把字面值更新成 81／17」**：後者把一個已知會再犯的缺陷保留到下一季。

### 決策三：新 MEGA 的特性取自 Bulbapedia infobox 的 `abilitym`，經 overlay 供應

超級具甲武者與超級戟脊龍在 PokeAPI 有基礎數值與圖檔、但沒有特性列。overlay 的定義正是「上游沒有來源的欄位」，且要求每筆記錄來源與刪除條件。

兩筆的 ability id 都已存在於 PokeAPI（181 Tough Claws、270 Thermal Exchange），所以**不需要合成 ability**，也就不必動用 overlay 的 `abilities` 區塊與那套 90001 起跳的合成 id。

**不採「暫時排除這兩個形態」**：母物種已在名單中，排除會讓形態切換器少掉一個上游明載的形態，而理由只是我們沒去找來源。

### 決策四：overlay 的三筆 `megas` 直接刪除

三筆的 `_delete_when` 都是「Bulbapedia 的 Champions 頁把它列為正式列」，條件已成立；`parse.py` 自己也會在條件成立時以斷言擋下來。

值得記錄的是：三筆當初推定的屬性與上游現在給的**完全一致**（超級阿勃梭魯Ｚ 惡／幽靈、超級烈咬陸鯊Ｚ 單一龍、超級路卡利歐Ｚ 格鬥／鋼），所以刪除不改變任何輸出值。這一點在驗證時是有用的：若刪除後這三個形態的屬性有任何變化，就是刪錯了東西。

### 決策五：規格的 Example 值以測試的實際輸出為準，而非以人工推算填入

部分 Example 值（查詢結果筆數）是查詢述詞作用在資料集上的結果，不是資料集本身的計數。人工重算等於在規格裡重新實作一次述詞 —— 而測試之所以有證據力，正是因為它匯入受測模組而不是重寫它的述詞。

作法：資料集落地後執行測試，每一列失敗會報出實際值；把規格值改為實際值，並逐列確認說明欄仍然描述得對（例如 `mega` 那一列必須仍然等於「帶有 MEGA 形態的種類數」，實測為 76）。**說明欄對不上時要停下來**，那代表語意變了而不只是數字變了。

### 決策六：招式機制在頁面間衝突時，取上游修訂時間最新的頁面

M-C 帶進第一組衝突：Wish 與 Strength Sap 的 PP 在不同學習表頁面上是 8 或 12。M-B 下沒有任何衝突（以原 208 份學習表重跑聚合步驟確認過），所以這是新出現的。招式自身的頁面只列出 Champions 的學習者，沒有該作專屬的 PP，無法裁決。

現行行為是**先到先贏且只印訊息不中止** —— 這兩筆的 PP 因此取決於物種頁的解析順序，而解析順序不承載任何權威性。

**規則：衝突時取上游修訂時間最新的那一份。** 理由是 Champions 會對招式做平衡調整，較舊的頁面可能早於調整；實測也相符 —— 帶 8 的三份（Pawmot、Arboliva、Indeedee，2026-09-10 17:59 至 20:42）都晚於帶 12 的各份（同日 16:03 至 16:06）。修訂時間由 MediaWiki API 取得並隨學習表一起快取，所以規則的輸入是上游中繼資料，不是我們的判斷。

**不採多數決**：多數只反映有多少頁面尚未被編輯到，與哪個值是現行值無關。**不採維持先到先贏**：那讓輸出取決於解析順序。**不採中止**：那會為了兩筆 PP 擋住整批更新。

時間戳相同而值不同時視為硬錯誤 —— 該情形下沒有任何依據可選，而安靜挑一個正是這條決策要消除的事。

## Implementation Contract

### 範圍內

**Pipeline 行為**

- 解析步驟在「其他形態」之後接任何第二層標題時，都要取得完整的該區段內容。以 M-C 的名單頁為輸入時，其他形態列為 87 筆、MEGA 列為 81 筆、無法轉移列為 0 筆。
- 抓取步驟對學習表分類的成員數斷言為 231，訊息文字一致。
- 抓取步驟同時取得每一份學習表頁面的上游修訂時間並快取，與學習表本身一樣可重複執行、已存在即略過。
- 聚合步驟偵測到同一招式在不同頁面上機制不一致時，採修訂時間最新的頁面之值，並印出勝出頁、落敗頁與雙方時間戳；時間戳相同而值不同時以非零結束碼中止。以 M-C 為輸入時，Wish 與 Strength Sap 的 PP 皆為 8。
- 組裝步驟的三項斷言為：種類 231、MEGA 形態 81、地區形態 17。
- 產出的 meta 中，`megas` 與 `regional` 由形態資料算出；`roster` 為指明 M-C 與其結束日期的字串；`species`、`formEntries`、`moves`、`abilities`、`moveRefs`、`zhMoves`、`zhAbilities`、`abilDescZh`、`abilDescEn` 維持計算。
- overlay 不再供應任何 roster 列；它供應的兩筆特性各自帶有來源與刪除條件。

**資料集**

以 M-C 輸入跑完後，資料集的規模計數為：種類 231、形態筆數 396、MEGA 81、地區形態 17、招式 511、特性 215、招式參照 15472。招式中有 415 筆的威力／命中／PP 與本傳數值不同，且全部 511 筆的數值來自 Champions 來源。

**應用層**

資料層的六項載入期不變式與上列相同的六個數字一致；任一不符時仍然拋出具名錯誤並同時報出期望值與實際值（此行為不變，只換期望值）。

**規格與測試**

八份規格的 Example 值與資料集一致。測試檔隨其規格的 Example 表變動。

### 範圍外

- 任何畫面、樣式、互動、效能行為
- `press-feedback` 與 `visible-range-window` 兩份規格
- 席多藍恩與超級席多藍恩
- PokeAPI CSV 與 52poke 快取的重抓

### 驗收條件

- pipeline 由乾淨狀態跑完步驟 0 至 8 且無非零結束碼；緊接著再跑一次，`design/champions-dex.json` 與 `src/data/dex.json` 兩者皆逐位元不變
- `pnpm run check` 每一項印出 ok
- `pnpm run typecheck` 通過（`vue-tsc`，不可代以 `tsc`）
- `pnpm test` 全綠，且任何筆數變動都能對應到本文件記載的資料集變動
- 三個原 overlay MEGA 形態的屬性在新資料集中與刪除前相同
- 聚合步驟印出的衝突裁決恰為 Wish 與 Strength Sap 兩筆，且資料集中兩者的 PP 皆為 8
- 裝置驗收：招式分頁與任一新物種的學習表可捲動、招式名維持單行不折行

## Risks / Trade-offs

- **以快取的 PokeAPI CSV 組裝新物種** → 隔離試跑中 183 個形態全數解析出中文標籤與已驗證圖檔路徑，且 Mega 命名規則對 42 個實例零不符；若日後有人清掉快取重抓而數字變動，那是一次來源更新，應當另案處理而不是併入本次。
- **招式表成長 15 筆，最寬招式名可能超出欄寬** → 規格記載目前最窄情形仍餘 10.5px。新招式名須重新確認；且網頁預覽量到的拉丁文字寬度不可信（像素字型在預覽中不載入），須依 HANDOFF §12 的作法量測。
- **衝突裁決依賴上游修訂時間** → 若某次編輯只動排版卻順手更新了時間戳，規則會偏向一份內容未變的頁面；但兩份的值相同時本就不構成衝突，僅在值不同時才有影響，且輸出會印出雙方時間戳供人判讀。
- **一次改動八份規格** → 分兩次做會讓測試在兩次之間是紅的，因為資料集與 Example 值互為對照。因此只能同時落地，代價是這個 change 偏大。

## Migration Plan

無資料遷移與相容性問題：資料集是編譯期內建資產，使用者端沒有任何持久化狀態依賴它的規模。`display-persistence` 持久化的只有色彩模式與語言兩項。

回滾即還原本次所有檔案變更；由於 pipeline 是純函式性的（同輸入同輸出），還原後重跑會回到 M-B 資料集，前提是名單頁與分類頁的快取檔一併還原 —— 那兩份是抓取步驟的輸入快取，不會自行回溯。

## Open Questions

無。原本掛在此處的招式機制衝突已由決策六解決：以 M-B 的 208 份學習表重跑聚合步驟，確認衝突為本次新增；裁決規則與其輸入來源已寫入契約。

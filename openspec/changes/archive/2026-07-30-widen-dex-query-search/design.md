## Context

搜尋框的佔位字承諾「名稱 / 編號 / 屬性 / 形態」，實作只做名稱。詳情見 proposal 的 Root Cause —— 簡短版是：規格當初只要求物種名的跨語系比對，實作照做了，而佔位字是從設計稿原樣搬過來的，描述的是設計稿的行為。

設計稿的做法已經讀過，它把九類欄位串成一個 haystack 並逐詞比對，另外用形態標籤的命中決定卡片顯示哪個形態。**這批不是照搬** —— 實測發現設計稿那條形態選擇規則有一個會回歸既有驗收的缺陷，見下面第三個決定。

以下數字都是對 `src/data/dex.json` 實算得到的，不是估計。

## Goals / Non-Goals

**Goals:**

- 佔位字承諾的四件事都成立：名稱、編號、屬性、形態
- 多詞查詢可用，且語意是「每個詞都要命中」
- 卡片顯示的形態回答查詢最具體指認的那件事，而不是無條件顯示基本形態
- 既有的名稱比對行為零回歸，包含前批已在實機驗收過的那幾項

**Non-Goals:**

- 不動排序、屬性鈕、世代鈕、重設鈕、佔位字
- 不加模糊比對、拼字容錯、搜尋語法（欄位前綴、引號片語、排除詞）
- 不做防抖或預先索引
- 不改招式表

## Decisions

### 搜尋語料建成單一 haystack 並逐詞比對

一個物種的語料是這些欄位串起來後轉小寫：中英物種名、中文分類、編號（`475` 與 `0475` 兩種寫法）、`gen<n>`、每個形態的中英標籤、跨全部形態的屬性英文名與屬性中文名。查詢以空白切詞，**每個詞都要出現在語料裡**才算命中。

替代方案與為什麼不採用：

- **逐欄位分別比對再取聯集**：等價於 haystack 但要寫九個分支，而且多詞語意會變得難講清楚（「詞 A 命中名稱、詞 B 命中屬性」算不算命中？haystack 的答案是算，而那正是想要的）
- **整串當一個子字串**（現況）：`mega charizard` 落空，因為沒有任何單一欄位同時含這兩個詞

代價是子字串比對會跨欄位邊界（語料裡相鄰兩欄的尾與首拼起來可能湊出一個詞）。用空白 join 讓這件事只在含空白的查詢詞上才可能發生，而那類詞已經被切開了。

### 不收錄設計稿的裸羅馬數字世代 token

設計稿的語料含 `GEN_ROMAN[sp.g]`，也就是 `V`、`IX` 這類。**實測搜 `V` 命中 208 筆裡的 125 筆** —— 任何名稱含字母 v 的物種（Venusaur、Vileplume、Vaporeon…）。

單字母 token 命中六成資料集，畫面上與「搜尋壞了」無法區分。`gen5` 沒有這個問題（實測 29 筆，等於世代鈕選 5 的結果集），所以保留 `gen<n>` 而拿掉裸數字。

順帶一提：佔位字承諾的四件事**不含世代**，所以世代 token 本來就是額外的便利而非契約。拿掉裸數字不減少任何承諾。

### 卡片形態的選擇改為四層優先序，且先扣掉物種名已滿足的詞

**設計稿那條規則不能照搬。** 它判斷一個形態是否被查詢命中的條件是「該形態的標籤含全部查詢詞」，而 Mega 的標籤本身就嵌著物種名 —— 於是**搜 `charizard` 會顯示 Mega Charizard X**，因為 `Mega Charizard X` 這個標籤含 `charizard`，而基本形態的標籤是空字串被跳過。這會回歸前批已在實機驗收過的行為。

改法是先把**物種名已經滿足的詞扣掉**，剩下的詞才拿去比對形態：

| 層 | 判準 | 為什麼 |
|---|---|---|
| 1 | 剩餘詞全部命中某形態的中英標籤 → 該形態 | 查詢指名了形態 |
| 2 | 剩餘詞裡有屬性名（英文或中文，**全等而非子字串**）→ 帶該屬性的第一個形態 | 查詢指名了屬性。這與屬性鈕的規則同源 |
| 3 | 屬性鈕有選 → 帶該屬性的第一個形態（既有行為，不變） | |
| 4 | 以上皆無 → 基本形態（既有行為，不變） | |

第 2 層用全等比對而不是子字串，否則 `龍` 會把任何含「龍」的詞都當成屬性名。

實測結果（噴火龍 #6，三個形態）：

| 查詢 | 顯示 | 經由 |
|---|---|---|
| `charizard`／`噴火龍` | 基本形態 Fire/Flying | 第 4 層（剩餘詞為空） |
| `mega charizard` | Mega Charizard X | 第 1 層 |
| `mega charizard y` | Mega Charizard Y | 第 1 層 |
| `dragon` | Mega Charizard X Fire/Dragon | 第 2 層 |
| `龍` | 基本形態 Fire/Flying | 第 4 層 —— `龍` 在「噴火龍」裡，所以被扣掉了 |
| `fire` | 基本形態（它就帶 Fire） | 第 2 層 |

最後兩列值得看一眼：**查詢最具體指認了什麼，卡片就回答什麼**。`龍` 是這個物種名字的一部分，所以回答物種本身；`dragon` 不在名字裡，只能是屬性，所以回答帶那個屬性的形態。這不是特例處理，是扣詞這個動作自然的結果。

### haystack 即時組出，不預先建索引

每次比對時組出語料字串，與既有的「208 筆每次按鍵全量重算」同一個判斷。既有需求已明文記載那是刻意的，語料變寬不改變它 —— 從兩個欄位變成九類欄位，量級仍然是 208 乘一個小常數。

真的在裝置上感覺到延遲時再處理，而處理方式是預先算好每個物種的語料字串（它只依賴資料集，資料集是不變的），不是防抖。

## Implementation Contract

**行為（使用者觀察得到的）**

在搜尋框輸入 `475`，網格只留艾路雷朵一張卡。輸入 `0475` 同樣。輸入 `dragon`，留下 19 張卡，且噴火龍那張顯示的是 Mega Charizard X 的圖與 Fire/Dragon 的屬性列。輸入 `mega charizard`，只留噴火龍一張，顯示 Mega Charizard X。輸入 `alola`，留下雷丘與九尾，兩張都顯示阿羅拉的樣子。輸入 `gen5 dragon`，只留三首惡龍。

既有行為不變：`charizard`、`CHARIZARD`、`char`、`噴火龍`、`噴火` 仍各自命中噴火龍且**顯示基本形態**；`ditto` 仍只命中百變怪；切換主導語系不改變任何結果集。

**介面**

- `src/state/query.ts` 內的比對函式改為對 haystack 逐詞比對；決定卡片形態的函式改為四層優先序。兩者都是模組內部函式，`results` 的形狀不變（仍是 `{ species, formIndex }` 的序列）
- `src/data/dex.ts` 新增一個回傳某物種搜尋語料的存取器。放在資料層是因為它只依賴資料集，而且日後要預先算好時只有這一處要改
- 匯出面不移除任何東西，`QueryBar.vue` 與 `DexGrid.vue` 不動

**失敗模式**

- 查詢只有空白時視為空查詢，回全部 208 筆（既有行為）
- 查詢詞命中零筆時網格顯示既有的空結果說明，不向 console 回報
- 屬性名的全等比對在查詢詞不是屬性名時單純不觸發第 2 層，不拋錯

**驗收方式**

以腳本對真實資料集實算，逐項比對 proposal 的 Success Criteria 數字：編號 1 筆、`dragon` 19 筆且等於屬性鈕 Dragon 的結果集、`龍` 25 筆、`mega` 與 `超級` 各 73 筆且相等、`gen5` 29 筆且等於世代鈕 5 的結果集、`alola` 與 `阿羅拉` 各 2 筆、`火焰寶可夢` 2 筆。回歸項單獨列一組。形態選擇以上表六列逐列驗。

`pnpm run check` 與 `npm exec tsc -- --noEmit -p src/tsconfig.json` 皆通過。

**範圍邊界**

- 在範圍內：搜尋語料、逐詞比對、卡片形態的四層選擇、`dex-query` 的兩條需求
- 在範圍外：排序、三個鈕、佔位字、任何元件、招式表、資料層產出、防抖與索引

## Risks / Trade-offs

- **子字串比對讓屬性名與物種名互相干擾** → 這是既有「部分名稱比對」需求的必然結果，不是新缺陷。`龍` 命中 25 筆而非 19 筆已寫進 Success Criteria 當**預期值**，不是待修項
- **第 1 層可能選到非預期的形態** → 剩餘詞全部命中才算，且取第一個。`mega charizard` 得到 Mega X 而不是 Y 是文件順序決定的，與形態切換器的分組順序一致
- **扣詞這一步依賴物種名，所以名字含屬性字的物種行為與不含的不同** → 這是刻意的，見第三個決定的最後兩列。風險是後人覺得不一致而「修正」它，所以理由寫在 spec 的 Example 裡而不只在這裡
- **回歸既有實機驗收過的行為** → 回歸項單獨列一組驗，且 `charizard` 顯示基本形態這一條就是設計稿規則被拒絕的原因

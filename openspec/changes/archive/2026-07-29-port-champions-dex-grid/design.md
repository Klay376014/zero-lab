## Context

第一個垂直切片（已 archive）落地了資料層、POCKET／MODERN 兩個模式的 token、對比墨色判定、屬性字符與單張種類卡。App.vue 目前是那個切片的驗證載具：縱向堆疊模式與語系切換鈕、七張手挑的邊界案例卡、十八個字符乘兩種表面的色板，以及 96px 與 192px 的 sprite 放大對照。它不是產品畫面，設計上就預期被網格取代。

三個約束來自實測而非推論，全部記在 design/HANDOFF.md：

- **Lynx 不會自動捲動整頁**（§12.12）。macOS 桌面版視窗固定 800×600，載具內容約三屏高，字符色板與放大檢查在原生上完全到不了 —— 不是被裁掉，是沒有捲動機制。這條在 web 目標上不會暴露出來。
- **屬性字符的原生渲染沒有證據**。macOS 桌面版四種寫法只有 image 元素指向真實 SVG URL 能畫出來，content 屬性與 data URI 都空白（§12.10）。而真機掃碼實測尚未執行，所以 type-glyph 的需求目前是靠 web 目標與桌面版的殘缺證據支撐。
- **list 元素在這個框架版本上只支援尾端追加**。Vue Lynx 文件在 list 與 scroll-view 的比較頁自己註明 framework-side cell recycling「still open」（vue-lynx issue #302），而讀 `node_modules/vue-lynx/main-thread/` 的原始碼證實了更強的一件事：remove 與 update action 都沒有實作。詳見下方的容器決策 —— 這條在實作期才發現，並改變了原本的容器選擇。

另外 retro-theme 需求 2 的散文與它自己的 scenario、tasks 及 HANDOFF §12.7 的實測值互相矛盾（三 vs 四），而網格切片是氛圍層抖動的落地位置，抖動的作用正是引入額外色階。

## Goals / Non-Goals

**Goals:**

- 208 種類全部可瀏覽，卡片區有自己的捲動容器且記憶體行為經過裝置實測
- 整頁捲動結構成立，超過一屏的內容不再到不了
- 搜尋、屬性篩選、世代篩選、排序可用；搜尋永遠跨語系
- 篩選命中時卡片顯示的是命中的那個形態，不是固定的基本形態
- 首次載入有階梯揭示，且不會在捲動或篩選時重播
- 屬性字符的原生渲染策略在 iOS 上定案並回寫交接文件
- retro-theme 的顏色數矛盾修正，五份規格的 Purpose 補齊

**Non-Goals:**

- **氛圍層的有序抖動** —— 設計稿用 canvas 產生抖動 tile，而 Lynx 的元素清單裡沒有 canvas。替代方案（建置期預先產生 PNG、或 SVG pattern）是一個獨立問題，而且它純屬裝飾，不該綁住網格的正確性。另案處理
- **詳情面板、形態切換器、種族值條、特性、可學會招式表** —— 下一個切片
- **Literata 襯線體** —— 只服務特性說明與 footer 長文，兩者都在詳情面板切片
- **bundle 切分** —— 先量再決定。若 208 張卡進 list 之後首屏沒有實際問題就不動；要切的話切割線是資料集的 moves 與 sec 兩個大欄位
- **響應式欄數** —— 目標是手機，欄數固定。桌機寬度的版面不在這個切片的驗收範圍
- **無限載入／分頁** —— 208 筆是有界的已知資料集，不需要補資料
- **替 vue-lynx 的 list 元素補上 remove 與 update action** —— 本切片不打 patch、不送上游。這件事記在交接文件裡，等有裝置能驗 native 的 update-list-info 協定時再談
- **species-card 的需求變更** —— 卡片契約已經是 species 加 form index，篩選替換形態靠傳入不同 index 達成

## Decisions

### 長列表用 scroll-view 承載，因為 list 元素在 vue-lynx 尚不可用於會變動的序列

原本的判斷是用 list：Lynx 文件的判準是內容超過三屏、資料同質時用 list，而 scroll-view 不回收子節點。208 張卡符合前者。**實作時讀了 vue-lynx 的原始碼，發現這個判準在這個框架版本上不成立。**

`node_modules/vue-lynx/main-thread/` 的實際行為（讀程式碼，不是讀文件）：

| 位置 | 行為 |
|---|---|
| `insertListItem` | 只做尾端 push，忽略傳入的 anchor，因此無法插入到指定位置 |
| `flushListUpdates` | `removeAction` 與 `updateAction` 硬編為空陣列；只回報索引大於已回報數的新項目；已回報數永不遞減 |
| `OP.REMOVE` | 移除原生元素，但不把該項目從內部的 list 項目陣列移除 |

合起來：**list 只支援尾端追加**。序列因篩選變短時更新函式直接跳過，畫面留著舊項目；排序改變順序時內部陣列永遠是插入順序，格子與內容錯配。已抓 0.5.1（npm latest）的 tarball 逐段比對，行為一字不差；1.0.0 的 tarball 只有 171 bytes、是佔位 stub 不是真套件，所以升級不是出路。

同時要記一筆：**官方 guide 描述了 LIS 移動偵測與 remove/reorder 支援，與出貨的程式碼不一致。以程式碼為準。**

這也推翻了原本選 list 的理由本身。文件在 list 與 scroll-view 的比較頁自己註明 framework-side cell recycling「still open」（vue-lynx issue #302），而上面這段程式碼證實了它。所以現在選 list 換不到回收，還要賠掉篩選與排序的正確性 —— 取捨的兩邊都是負的。

因此改用 scroll-view 承載卡片區：篩選與排序回到普通的 Vue 協調，立即正確。代價是不回收，而 208 筆是有界的已知集合，所以把記憶體行為改成在裝置上實測（本來就是驗收項）而不是靠元素選擇來假設。日後 vue-lynx 實作了 remove 與 update action，這個決策要重新評估 —— 屆時 scroll-view 換 list 的改動範圍限於網格元件一處。

被否決的替代方案：**維持 list 但把篩選排序拆到下一個切片**（網格沒有搜尋不算可用，而查詢層已經寫好了）；**每次查詢改變就重建整個 list**（內部狀態以 list 的 id 為鍵存在 Map 裡且沒有對應的清理路徑，每次按鍵都會留下一份 → 記憶體無界成長）；**打 patch 自己實作 removeAction**（要摸索 native 的 update-list-info 協定，而那只有在裝置上才驗得出來，風險與時間都不可預估）；**第三方虛擬捲動套件**（文件明確警告這類套件依賴 DOM 量測，與 Lynx 的雙執行緒架構不相容）。

整頁結構：固定的 masthead 與查詢列在捲動容器之外，scroll-view 只承擔卡片區。這樣查詢列不會跟著卡片捲走，也避免兩層捲動搶手勢。

### 卡片的 key 由種類編號與形態索引組成，不用陣列位置

篩選會同時改變序列長度、順序，以及每張卡顯示哪個形態。若用陣列位置當 key，Vue 會把既有的卡片元件重用到不同的species與形態上，而卡片內部持有 sprite 的載入狀態（載入成功才移除替代圖塊）—— 舊的載入狀態會套到新的圖上，症狀是圖已經換了卻還蓋著上一張的屬性字符，或反之。

所以 key 取種類編號與形態索引的組合。形態索引必須進 key：同一個species在不同屬性篩選下顯示不同形態，只用編號會讓 Vue 認為是同一張卡而不重建載入狀態。

### 網格用 flex-wrap 與佔行比例的儲格排出欄位

scroll-view 沒有 list 的 flow 版型與 span-count，所以欄位由容器的 flex-wrap 加上儲格寬度決定。容器沿用第一個切片的 `.Cards`（row 方向 flex-wrap），不新寫一套。

**原本的決定是沿用固定的 164px 卡片寬度，iOS 實機推翻了它。** 水平 chrome padding 是每側 33px（Root 12 + Shell 9 + Screen 12）共 66px；一張卡外圍 `164 + 6 margin = 170`，兩張需 340px。iPhone 邏輯寬度 375／390／393 扣掉 chrome 只剩 309／324／327，**全部放不下兩欄**，只有 430 的 Plus / Pro Max 放得下。原因很明確：設計稿的 164px 是為「最窄 500px 的瀏覽器」調的（500−66 = 434，兩張剛好），從來沒有為 390px 的手機驗過。一個 208 種類的網格在半個螢幕寬的單欄下不算可用。

所以儲格寬度改成佔行的一半，欄數由比例決定而不是由寬度相除。這仍然不需要螢幕寬度查詢 —— CSS 的百分比就是那個除法 —— 但結果在每個目標寬度上都是兩欄，而不是「看裝置決定」。

實作上有一個平台細節在幫忙：**Lynx 的 `box-sizing` 預設是 `border-box`**（web 是 `content-box`，見 §12.7），所以宣告的寬度已含邊框與 padding，兩個各佔一半的儲格正好填滿一行不會溢出。**因此欄間留白必須是儲格的 padding 而不是 margin** —— margin 會加在寬度之外，把第二個儲格擠到下一行。

卡片的 sprite 維持 96px 並置中，所以儲格寬度變成比例不影響像素整數倍放大那條 —— 放大依賴的是圖自己的尺寸，不是容器的。

代價：寬螢幕會是兩張大卡而不是四張小卡。目標是手機，桌機版面仍不在驗收範圍；真要分欄再多一級時，改的是那一個比例值。

### 查詢狀態放獨立模組，不在 list 之上包抽象層

搜尋字串、屬性篩選、世代篩選、排序方式放進新的查詢狀態模組，沿用既有顯示狀態模組的模式：模組層級 refs 加 computed，不透過 props 貫穿整棵樹。理由與當初一樣 —— 每個要畫的元件都需要當前查詢結果，貫穿等於在整棵樹上加 prop。

網格元件直接持有 list 元素，**不包一層自己的虛擬化或列表抽象**。刪掉那種轉手層什麼都不會壞，它不該存在。真正該藏在查詢模組後面的是有內容的推導：跨語系比對、當前篩選下每張卡該顯示哪個形態、排序鍵取值。

### 搜尋永遠跨語系比對

比對範圍同時包含中文與英文名稱，不隨主導語言改變。設計稿的既有行為就是這樣：語系切換改的是「哪個語言主導」，不是資料的可見範圍。使用者輸入 charizard 或 噴火龍 都應該命中同一筆。

被否決的替代方案：只比對當前主導語言（使用者切語系會讓已輸入的查詢突然無結果，是壞掉的觀感）。

### 排序鍵取最強形態的種族值總和

重用資料層既有的衍生存取器取得species的最強形態總和。取基本形態會把所有 MEGA 埋在低數值下面 —— 妙蛙花基本 525、Mega 625，用基本形態排序等於讓 75 個 MEGA 在榜上消失。

屬性與世代篩選同樣是species層級的判定：屬性用資料層既有的跨形態屬性集合存取器，所以篩「龍」會命中只有 Mega 形態才是龍的species。

### 篩選命中的形態由網格推導後傳入卡片

卡片的輸入契約不動（species 加 form index）。網格在當前篩選下為每個命中的species算出應該顯示哪個形態的索引，再傳給卡片。

理由是設計稿的既有決策：否則篩「龍」會用火／飛行的圖回答，看起來像壞掉。推導規則是取第一個滿足當前屬性篩選的形態；沒有屬性篩選時取基本形態。

這也是為什麼 species-card 不需要修改 —— 這個行為的歸屬是查詢，不是卡片。

### 階梯揭示只在首次載入播放一次，之後進入序列的卡片不重播

動態用 steps() 而非平滑 easing（那個年代的掌機沒有補間，平滑 easing 會讀成錯的年代），延遲隨索引遞增但有上限，超過上限的卡片延遲相同 —— 208 乘每格延遲會讓最後一張等好幾秒。用 scroll-view 之後全部 208 張在首次繪製就掛上，所以這個上限比原本更重要，不是可選的優化。

需要一個開機旗標的理由與設計稿不同。設計稿防的是「每次篩選都重播讓操作感覺變慢」；這裡多一種情況：清掉篩選會讓卡片重新掛上，掛上就會觸發進場動畫，於是放寬篩選看起來像整頁重載。解法沿用設計稿既有的機制 —— 揭示動畫綁在一個開機旗標上，首次繪製完成後移除旗標，之後任何進入序列的卡片都不帶動畫。

（原本用 list 元素時這條是為了防回收重用的格子閃動。改用 scroll-view 後沒有回收，但同一個機制解的是同一件事：動畫只該屬於第一次。）

### 先在 iOS 結清字符渲染策略，之後才替換驗證載具

順序是硬的：現有的驗證載具就是字符色板與 sprite 放大對照的載體，一旦換成網格就沒有東西可以拿來做那場對照實測。所以 iOS 實測必須跑在 App.vue 被改動之前。

實測內容是 HANDOFF §12.10 的四種寫法對照：svg 元素的 content 屬性、svg 元素的 src、image 元素指向 SVG 檔、image 元素指向 SVG 的 data URI。判定結果決定 TypeGlyph 元件動或不動：

- content 在 iOS 成立 → 元件不動，桌面版標記為不能用來驗字符
- content 不成立 → 改用 image 元素指向 SVG 資產搭配 tint-color。**不為十八屬性乘表面乘模式產生上百個檔案** —— tint-color 對非透明像素上色，所以十八個單色 SVG 加上依表面決定的 tint 就夠。data URI 在桌面版已實測是死路，必須是真實資產

無論哪個結果都回寫 design/HANDOFF.md，讓下一個切片不必重查。

### POCKET 顏色數上限更正為四

retro-theme 需求 2 的散文寫「SHALL remain three」，但它自己的 scenario 允許到四、tasks 明寫上限四非固定三、HANDOFF §12.7 記載三是舊數字而實測靜止狀態是四（卡片斜角的次級表面色在靜止時就會上色）。

更正為「不超過四」。這條不變式真正要防的是引入色盤外的顏色，不是把數字釘在某個值上 —— 而網格切片正是氛圍層抖動的落地位置，散文那個「三」會直接誤導實作判斷。

## Implementation Contract

**Behaviour**

啟動後看到的是網格畫面而非驗證載具：固定的 masthead 與查詢列，下方是可捲動的多欄卡片網格，208 種類全部可瀏覽到底。首次載入時卡片以階梯方式逐格揭示，之後捲動與篩選都不再播放揭示動畫。

查詢列可輸入搜尋字串、選屬性、選世代、切排序方式。搜尋輸入 charizard 與 噴火龍 命中同一筆，且切換主導語系不改變命中集合。選定屬性後，命中species的卡片顯示的是命中該屬性的形態 —— 篩選「Dragon」時噴火龍的卡片顯示 Mega 噴火龍 X 的圖像、標籤與屬性，而不是基本形態的火／飛行。排序切到種族值時，以每個species最強形態的總和遞減排列，所以 Mega 班基拉斯所屬的species排在前段而非被基本形態的數值埋掉。

查詢無命中時網格區顯示一則說明文字而非空白區域。

**Interface / data shape**

新增查詢狀態模組，與既有顯示狀態模組同層。對外暴露：四個可寫的查詢狀態（搜尋字串、屬性篩選、世代篩選、排序方式）、一個 computed 的查詢結果序列（每個元素同時帶species與該筆在當前篩選下應顯示的形態索引），以及重設查詢的函式。排序方式是一個封閉集合，至少含編號與種族值總和兩種。

新增網格元件，輸入是查詢結果序列，內部持有 scroll-view。每張卡的 key 是由種類編號與形態索引組成的值，不是陣列位置。欄位由既有的 row 方向 flex-wrap 容器樣式加上既有的固定卡片寬度決定，垂直捲動。

既有的字串表補上查詢列與空結果的字串，zh 與 en 兩組鍵集必須相同（既有的不變式）。字串來源是設計稿 pipeline 的 HTML 模板裡的 I18N 表，不新編。

若字符渲染退路啟用，TypeGlyph 的輸入契約（屬性加目標表面）不變，只換內部渲染方式與新增 SVG 資產目錄。

**Failure modes**

- 資料層的六項載入期斷言行為不變：違反時丟出含不變式名稱、期望值、實際值的錯誤，不靜默降級
- sprite 載入失敗沿用既有的替代圖塊策略（靠 load 事件而非 error 事件，因為原生上 error 不觸發），卡片高度不變、console 不報錯
- 未知屬性名沿用既有的回退到 Normal，不丟錯
- 查詢無命中不是錯誤：顯示說明文字，console 不報錯
- 字符渲染在裝置上不成立時，退路是換渲染方式而非隱藏字符。字符完全不可見是驗收失敗，不是可接受的降級

**Acceptance criteria**

- 建置通過且無屬性錯誤
- iOS 實機上四種字符寫法的對照結果逐項記錄，判定寫進 design/HANDOFF.md，並明確標記採用哪一種
- iOS 實機上捲動到 208 筆的最後一筆，過程中無空白格、無錯格內容
- 記憶體行為實測：捲動全程觀察是否隨已捲過的筆數持續成長，並把實測結果記進交接文件。scroll-view 不回收是已知的，要量的是 208 筆在手機上是否可接受
- 搜尋 charizard 與 噴火龍 各自命中同一筆；切換主導語系後命中集合不變
- 屬性篩選 Dragon 時，噴火龍的卡片顯示的屬性列是火／龍而非火／飛行
- 排序切到種族值總和時，第一筆的最強形態總和不小於第二筆
- 首次載入播放揭示動畫；捲動離開再回來的卡片不再播放；改變篩選不重播
- POCKET 下所有實際上色的顏色都落在四階灰之內，數量不超過四
- 兩個模式乘兩個語系四種組合的網格皆無破版，零水平溢出
- retro-theme 需求 2 的散文與其 scenario 一致；五份既有規格的 Purpose 皆非佔位字串

**Scope boundaries**

範圍內：新增網格元件與查詢狀態模組；改寫 App.vue 與 App.css 讓網格取代驗證載具；補字串表的查詢列與空結果鍵；iOS 實機實測與交接文件回寫；retro-theme 顏色數更正；五份規格的 Purpose 補齊；僅在實測判定需要時才改動 TypeGlyph 與字符字串產生模組並新增 SVG 資產。

範圍外：氛圍層抖動；詳情面板與其所有子部件（形態切換器、種族值條、特性、招式表）；Literata；bundle 切分；響應式欄數；無限載入補資料；species-card 的需求變更；資料層的任何欄位變更。

## Risks / Trade-offs

**scroll-view 不回收子節點，208 張卡全程掛在樹上** → 把記憶體行為列為明確的裝置驗收項。卡片結構淺（兩層 view 加七個文字節點與一張圖），sprite 是外部資源不佔 bundle，所以 208 筆有相當機會可接受 —— 但這是要量的，不是要假設的。真的不可接受時，退路是自己做視窗化：以捲動位移推算可見區間，只渲染區間內加上前後各一屏的卡片。這條退路不需要 list 元素，也不改變資料集有界的事實。

**改用 scroll-view 是為了繞過框架缺陷，不是因為它更適合** → 決策裡記了重新評估的觸發條件（vue-lynx 實作 remove 與 update action）與改動範圍（網格元件一處）。風險是這筆理由日後被讀成「這個專案偏好 scroll-view」而不是「當時 list 不能用」，所以同一份證據也寫進交接文件的平台事實一節。

**iOS 上 content 屬性可能也不成立** → 退路已經在桌面版實測過可行（image 元素指向真實 SVG URL），而且改動範圍限於 TypeGlyph 元件與字符字串產生模組兩處，卡片與篩選鈕都只透過屬性加表面兩個輸入使用字符，不會被波及。代價是新增十八個 SVG 資產與一次 tint-color 的對比重算。

**Android 的字型註冊仍未驗** → 手上沒有 Android 裝置，這條掛帳。影響範圍限於樣式表的字型註冊規則，且失敗模式是明顯可見的（拉丁文字落回系統字型），不會靜默通過。不阻擋本切片。

**驗證載具被網格取代後，字符色板與 sprite 放大對照就消失了** → 這是刻意的代價，換來的是產品畫面。因此 iOS 實測必須排在 App.vue 改動之前；順序反了就得為了重驗而把載具重建一次。

**固定欄數在桌機寬度下會顯得稀疏** → 接受。目標是手機，桌機版面不在驗收範圍，而欄數是單一常數，日後要響應式時只有一處要改。

**篩選替換形態會讓同一個species在不同篩選下顯示不同圖像** → 這是設計稿的刻意決策而非缺陷。代價是卡片的 key 必須含形態索引，否則 Vue 會把舊形態的卡片元件連同它的 sprite 載入狀態重用到新形態上。

**查詢是 computed，208 筆每次輸入都全量重算** → 208 筆的過濾與排序成本可忽略，不預先做索引或去抖。若實測輸入有延遲感再處理，現在做就是為想像的問題付複雜度。

## Context

招式表（`LearnsetTable`）目前只做一個方向的查詢：給定一個形態，列出它會的招式。反方向從未被開放 —— 資料集裡的 12,939 組學習關係，只能從物種那一端讀。

量測過的資料形狀，本設計的三個決定都由它決定：

| 事實 | 數值 |
|---|---|
| 有學習者的招式 | 496 / 496（沒有空清單這個情況） |
| 單一招式的最多學習者 | 207 隻（208 隻裡的 207；前五名都是 207） |
| 學習者數量中位數 | 14 隻 |
| 「招式 → 物種」配對總數 | 12,939 |
| 招式區段多於一份的物種 | 15 / 208（全為地區形態） |
| `form.si` 分布 | 0:341、1:16、2:2、3:1 |
| 只能經由非基本形態抵達的配對 | 174 / 12,939 = 1.3% |

平台與既有 spec 施加的約束：

- `species-detail` spec 只允許面板本體與招式表兩個捲動容器，並明文寫招式表「不是前例」。`ROADMAP.md` C 節另有一條補充：§12.19 實測巢狀同向捲動技術上成立，但那不是在其他區段加捲動區的通行證
- `ROADMAP.md` C 節禁止存取捲動位置的程式碼；`species-detail` spec 的 mount/unmount 需求把「每次開啟都從頂端開始」列為刻意的後果之一
- `press-feedback` spec 的控制項集合是列舉的，新增控制項就必須修改該條需求
- `design/HANDOFF.md` §12.14 記錄 208 張卡的首次繪製比直覺慢得多
- `design/HANDOFF.md` §12.16 記錄面板不得使用 `inset` 陰影與 grid 版面；`pnpm run check` 會驗前者

## Goals / Non-Goals

**Goals:**

- 由招式反查會該招式的物種，並在畫面上呈現
- 從該清單選中一隻物種時，詳情切換為該物種
- 切換後的面板從頂端開始閱讀，而不繼承前一隻物種的捲動位置
- 反查涵蓋所有形態的招式區段，而不只基本形態
- 既有的四項 `pnpm run check` 不變式維持通過，且涵蓋範圍不縮小

**Non-Goals:**

- 通用共用元件抽象層。全專案只有招式表一處顯示招式，沒有第二個使用者
- 返回堆疊。選取語意是取代
- 清單上的搜尋、篩選或排序控制項
- 重用 `SpeciesCard` 呈現清單
- 在詳情面板內部新增任何捲動區段
- 新增 `GlyphSurface` 成員
- 學習者清單本身的按壓回饋以外的動畫或揭示效果

## Decisions

### 反向索引以惰性 memo 建在資料層

「招式索引 → 會該招式的物種」的推導放在資料層，與 `allTypes` 與 `searchHaystack` 同層、同模式：以 `Map` 按招式索引記憶，第一次被問到才計算，計算過就不再變。

理由與那兩個既有 memo 相同且更強：`dex` 載入後全程唯讀，一個招式的答案不可能改變，所以沒有東西需要失效 —— 這是 memoisation，不是會 miss 兩次的 cache。

**替代方案：開機時一次建完 496 筆。** 一趟走完所有區段就能全部建好，程式更短。不採用，因為它把成本加在啟動路徑上，而 §12.14 已記錄該路徑比直覺慢；惰性版本讓從未被點過的招式不付任何代價，而中位數 14 筆的單筆計算是走 208 個物種的區段，可忽略。

### 學習者清單是詳情面板的兄弟層，不是面板內的區段

清單以自己的 overlay 呈現，在元素樹中與詳情 overlay 平行，疊在其上。它自帶捲動容器。

理由是最多 207 筆必須捲動，而放進面板就會是第三層同向巢狀捲動，同時違反 `species-detail` spec 對捲動容器數量的限制 —— 那條限制的違反在本平台是靜默的，`pnpm run check` 讀樣式表而不讀模板，看不到它。

**替代方案：在招式列底下就地展開。** 不採用，理由同上，且展開會把已捲動的招式表內容推走。

### 選取語意為取代，並以物種為面板的 reconciliation key

選中清單中的物種時，呼叫既有的 `openDetail` 取代選取，不維護來源堆疊。關閉詳情一律回到網格。

單純取代會產生一個問題：詳情面板的掛載條件是「有選取」，取代前後都成立，所以面板不會重新掛載，B 物種的面板會停在 A 物種當時的捲動位置 —— 使用者剛從招式表（面板底部）跳過來，看到的會是 B 的種族值中段。

解法不是讀寫捲動位置（`ROADMAP.md` C 節禁止），而是給面板一個以物種為值的 reconciliation key，讓物種切換等同於一次卸載與掛載。`species-detail` spec 既有的 mount/unmount 需求因此自動生效，不需要新機制。

招式表的排序與篩選狀態不受影響：它們刻意存放在模組層而非元件內，本來就跨掛載存活。

**替代方案：返回堆疊。** 選取改為陣列、加返回鈕。不採用，成本落在 `selection.ts` 與 `species-detail` spec 的掛載語意上，而使用者已確認取代即可。

### 形態挑選以基本形態優先，缺該招式時退到第一個含它的形態

開啟學習者時，若基本形態的招式區段含該招式，開基本形態；否則開第一個區段含該招式的形態。

98.7% 的配對走第一條分支。第二條分支存在是因為那 174 筆若一律開基本形態，會產生一個靜默錯誤的畫面：使用者為了某個招式點進來，而那個招式不在他看到的招式表裡。九尾是具體例子 —— 暴風雪、冰凍光束、極光幕等 18 個招式屬於阿羅拉的樣子（冰／妖精，`si` 為 1），基本形態（火）的 67 個招式不含任何一個。

這個失敗屬於 §12.17 記錄的類型：沒有錯誤、沒有空白、畫面完整，只是資訊不對。

**替代方案：一律基本形態。** 使用者最初的偏好，量測後改為折衷版。若改回，那 174 筆必須寫成 spec 中的已知偏離而非默默存在。

### 清單以兩隻一列的精簡列呈現，不重用種族卡

每列容納兩隻物種，每筆呈現物種名（依當前語系）、編號與型別標記。不使用 `SpeciesCard`。

理由是規模：207 張卡在第二層 overlay 裡等於再付一次 §12.14 記錄的首次繪製成本。精簡列的代價是與主畫面兩套呈現語彙，但清單的作用是導航而非瀏覽，兩者職責不同。

### 招式列成為控制項並加入按壓標記集合

招式表的每一列綁定 tap 以開啟學習者清單，並綁定三個 main-thread 觸控屬性以畫出按壓位移。

三個綁定必須成套：招式列位於詳情面板的捲動容器內，一個變成捲動的按壓只會產生 cancel 而永遠不會產生 release，`press-feedback` spec 已就這一點立下需求。

`press-feedback` spec 的控制項集合是列舉的，因此該條需求必須同時修改，否則新控制項處於「有標記但 spec 未涵蓋」的狀態。

### 本次引進的用語登錄到 openspec/LANGUAGE.md

本功能的核心概念在討論中有三種叫法：UI 端的「學習者清單」與「會該招式的寶可夢」，實作端的「反向索引」。混用會讓 artifact 讀起來像在描述兩件事。

建立 `openspec/LANGUAGE.md` 並登錄該概念的正規用語與應避免的同義詞。`CLAUDE.md` 已記錄該檔的第一筆會是同屬性攻擊加成的「本系加成／★ 屬修」，本次一併登錄。

## Implementation Contract

### 行為

- 在詳情面板的招式表中按下任一列，該列出現向下一像素的按壓位移；放開後開啟學習者清單
- 學習者清單覆蓋在詳情面板之上，標示該招式的名稱與學習者總數，並以每列兩隻的精簡列列出所有會該招式的物種
- 清單自身可捲動；詳情面板在其下方保持原狀
- 關閉清單（點遮罩或關閉鈕）回到原本的詳情面板，面板的捲動位置不變
- 在清單中選中一隻物種：清單關閉，詳情面板顯示該物種，內容從頂端開始
- 切換後關閉詳情面板，回到網格，而不是回到來源物種
- 切換後招式表的排序與屬修篩選維持切換前的設定

### 介面與資料形狀

- 資料層新增一個具名的衍生存取器，輸入為招式在共用招式表中的索引，輸出為會該招式的物種唯讀陣列，順序為資料集自身的物種順序。與 `allTypes` 相同，回傳的陣列由所有呼叫者共用，型別上以唯讀標註禁止變更
- 資料層新增一個具名的形態挑選函式，輸入為物種與招式索引，輸出為應開啟的形態索引：基本形態的區段含該招式時回傳基本形態的索引，否則回傳第一個區段含該招式的形態的索引
- 新增一個狀態模組，持有「目前正在檢視學習者的招式索引」，以及開啟與關閉它的具名函式。該模組與 `selection.ts` 平行，不由它擁有
- i18n 字串表新增本功能所需的鍵，中英兩份同時補齊；缺任一份會使該語系顯示鍵名而非文字

### 失敗模式

- 招式索引落在共用招式表之外：既有的 `moveOf` 已對此擲出並附診斷訊息，反向索引沿用同一條路徑，不新增第二種處理方式
- 學習者為空：資料上不可達（496 個招式全部至少有一隻學習者），因此不為此新增畫面狀態。若未來資料集改變而使其可達，反向索引回傳空陣列，清單呈現為零列而不是擲出
- 形態挑選找不到任何含該招式的區段：不可達，因為物種是由反向索引選出的，代表至少一個區段含它。此情況退回基本形態索引，不擲出 —— 擲在 computed 內在本平台呈現為無法解釋的版面破損而非錯誤

### 驗收條件

- `pnpm run check` 四項不變式通過，且對比檢查的涵蓋範圍不縮小（不新增 `GlyphSurface` 成員，故涵蓋範圍定義不變）
- `npm exec tsc -- --noEmit -p src/tsconfig.json` 無錯誤
- 樣式檢查不得因新樣式而失敗：新增的規則不得使用 `inset` 陰影、不得使用 grid 版面、不得出現 `font-variant-numeric`，且任何選中態規則不得被自身的基礎規則取消
- 實機驗收（本專案視為變更的一部分，非形式）：
  - 在招式數超過 12 的物種上，於招式表內按住一列並滑動使其變成捲動，放開後該列不得留在位移狀態
  - 開啟一個學習者數為 207 的招式，捲動該清單至末尾，確認詳情面板不隨之捲動 —— 這驗證兩層捲動依落點分派，與 §12.19 的既有結論一致
  - 於九尾的招式表中點選暴風雪，在清單中選回九尾，確認開啟的是阿羅拉的樣子且招式表含暴風雪
  - 從 A 物種切換至 B 物種後，確認 B 的面板顯示在頂端

### 範圍邊界

**在範圍內**：反向索引與形態挑選的資料層推導、學習者清單的狀態模組與元件、招式列成為控制項、詳情面板的 reconciliation key、本功能的 i18n 鍵、上述五份 spec 的異動、`openspec/LANGUAGE.md` 的建立。

**在範圍外**：`ROADMAP.md` A 節任何一項（本功能是新增範圍，不是補設計稿差距，A 節無項目可移除）、招式表既有的排序與篩選行為、`SpeciesCard` 與網格、清單上的搜尋或篩選、返回堆疊、`selection.ts` 的 clamp 邏輯。

## Risks / Trade-offs

- **207 列的清單在本平台的首次繪製可能明顯慢** → 精簡列的元素樹遠淺於種族卡，這是選它而非重用卡片的主因。實機驗收明列一次 207 筆的捲動測試；若仍不可接受，退路是為清單設上限並在畫面上聲明被截斷的數量，而不是靜默截斷
- **第三層 overlay 的定位可能不如預期覆蓋整個畫面** → `species-detail` spec 已為面板記錄過同一個平台問題與其退路（改為取代網格的全螢幕區域）。清單沿用面板已被實機證實可行的定位方式，不引進新的定位模式
- **招式列變成控制項後，捲動招式表時可能誤觸** → `press-feedback` 的 cancel 綁定處理視覺狀態，但 tap 是否在捲動後仍然觸發需實機確認。若會誤觸，退路是把可點區域縮到招式名稱本身而非整列
- **兩隻一列在中文長名或英文長名下可能溢出** → 與 `SpeciesCard` 面對的是同一個問題，該元件已有處理長名的既有做法可循；驗收時以最長的物種名檢查
- **反向索引的 memo 在資料集變更後仍然正確** → 依賴 `dex` 全程唯讀這個既有前提，與兩個既有 memo 相同。若未來引進任何會改動 `dex` 的路徑，三個 memo 會同時失效，這是既有風險而非本次新增

## Context

`src/data/dex.json` 是 `design/pipeline/` 的產物，`design/champions-dex.json` 是同一份資料的縮排版本，兩者不得手改。pipeline 的資料權威分工是刻意切開的：Bulbapedia 的 Champions 頁面供應名單、形態與招式機制，PokeAPI 的 CSV 供應種族值、特性與命名，52poke 供應招式的正體中文。

三個要加入的形態在這個分工下的狀態並不對等，這是本設計要處理的核心不對稱：

| 資料格 | 超級阿勃梭魯Ｚ | 超級烈咬陸鯊Ｚ | 超級路卡利歐Ｚ |
|---|---|---|---|
| Bulbapedia roster 列 | **完全沒有** | 有，但整行是 HTML 註解 | 有，但整行是 HTML 註解 |
| 屬性 | **無來源**，由使用者裁定為 Dark／Ghost | 註解列寫單屬性 Dragon | 註解列寫 Fighting／Steel |
| PokeAPI 種族值 | 有（id 10307） | 有（id 10309） | 有（id 10310） |
| PokeAPI 精靈圖 | 有，`10307.png` 經 HTTP 驗證回 200 | 有，`10309.png` 回 200 | 有，`10310.png` 回 200 |
| PokeAPI 特性 | **完全沒有** | **完全沒有** | **完全沒有** |
| PokeAPI 正體中文形態名 | **沒有**（只有日／法／英） | **沒有** | **沒有** |

三個精靈圖各自獨立、不與物種共用，因此不會觸發 pipeline 的近似圖旗標，詳情面板不會出現近似圖警語。

三個形態所屬的物種各自只有一段學習集，因此無論屬性是否改變，形態的學習集指標都會落在同一段 —— 招式庫共用不需要任何新機制。

## Goals / Non-Goals

**Goals:**

- 三個 MEGA 形態進入資料集，與各自物種共用既有招式庫
- pipeline 重跑能穩定產出同一份結果，且不吃進上游尚未上線的資料
- 上游日後正式補齊時，本次新增的 overlay 能整份刪除並以重跑驗證等價

**Non-Goals:**

- **不處理**席多藍恩、轟擂金剛猩、戟脊龍三個物種與超級席多藍恩、超級戟脊龍兩個形態。它們在 Bulbapedia 的學習集分類裡沒有頁面，招式庫無從取得
- **不補**鋒銳這個特性缺少的正體中文說明。該欄在既有資料集裡已經是空字串，屬於那 19 個沒有中文說明的特性之一，與本次變更無關
- **不改**形態切換器、卡片、詳情面板的任何版面或行為
- **不新增**任何非 Bulbapedia 的學習集來源

## Decisions

### 三個形態一律走 overlay，不從上游的註解列取得

`design/pipeline/parse.py` 學會跳過 HTML 註解之後，上游那兩筆註解掉的 Z 形態列也會一併被排除。這是刻意的：三個形態改由同一份 overlay 供應。

替代方案是讓烈咬陸鯊Ｚ 與路卡利歐Ｚ 走上游、只有阿勃梭魯Ｚ 走 overlay。否決的理由是那會產生兩條資料產生路徑，而三個形態在使用者眼中是同一批東西；來源分歧會讓「這個形態的屬性是誰決定的」這個問題在每次維護時都要重新查一次。單一 overlay 讓三筆的出處註解寫在同一個地方，且上游正式上線後可以整份刪掉、用重跑結果是否相同來驗證等價。

overlay 只需要供應 roster 列與特性兩件事。roster 列本身就帶著形態的英文標籤、屬性與名單狀態 —— 資料集的英文形態名取自這裡，不是取自 PokeAPI（PokeAPI 雖然也有，但 pipeline 不讀）。種族值與精靈圖路徑則由既有的形態比對與驗證步驟從 PokeAPI 自動取得，因為 PokeAPI 已經有 `absol-mega-z`、`garchomp-mega-z`、`lucario-mega-z` 三個變體，既有的比對邏輯能從形態標籤精確命中它們。

### roster 解析只採納正式上線的資料

上游以 HTML 註解預先排版尚未上線的資料，版本欄填 `X.X.X`。`design/pipeline/parse.py` 目前的樣板比對不認得註解，會把它們當成正式資料。本次抓取時這是八筆。

替代方案是在解析後於名單層級剔除不要的項目。否決的理由是那要維護一份「不要哪些」的清單，而上游每次預先排版新東西都會讓清單過期；剝除註解是描述「什麼算正式資料」，不會過期。

另一個替代方案是以版本欄 `X.X.X` 作為排除條件。否決的理由是那把兩件事綁在一起 —— 上游可能註解掉一筆已經有版本號的資料，也可能在正式列裡暫填版本號，兩種情況都會判錯。

這個決定與三個形態互相獨立，是這次變更裡唯一一項就算三個形態全部取消也仍然應該做的工作。

實作時證實這個缺陷已經發生過一次：上游的名單頁面在本次八筆之前就有一筆被註解掉的 Pawmot（923）列，舊的解析器把它當成正式資料，產出第 209 個物種。當時的處置是在三個下游檔案裡寫下四處 `dex != 923` 的手寫排除。剝除註解使那四處全部失效，因此一併移除 —— 保留一份針對單一編號的手寫排除，會與「註解列不得抵達任何下游步驟」這條規範互相矛盾，並讓下一個讀者以為 923 有什麼特殊之處。

### MEGA 中文名推導規則擴充到 Z，並記錄它驗不到

`design/pipeline/zh_forms.py` 以「超級 + 物種中文名 + 結尾的 X 或 Y 轉全形」推導 MEGA 的中文名，並以上游已在地化的 41 個 MEGA 驗證這條規則。Z 形態上游沒有正體中文名，所以擴充後的規則**不會被那個驗證涵蓋**。

規則寫錯的後果是安靜的：`Mega Absol Z` 若沒有匹配到 Z，會推導出「超級阿勃梭魯」，與既有的超級阿勃梭魯撞名，而形態切換器上會出現兩顆字完全相同的按鈕。因此擴充處要寫下這個驗證缺口，並在任務裡以實際輸出比對作為驗收，而不是依賴既有的斷言。

Z 採全形Ｚ，與既有的超級噴火龍Ｘ／Ｙ 一致。全形字落在半形全形形式區，與 CJK 同樣落回系統字型，樣式檢查的字型子集涵蓋範圍不受影響。

### 特性表新增波導防護，並接受索引整體位移

波導防護在 PokeAPI 完全不存在，由 overlay 供應四個欄位：英文名 `Aura Guard`、中文名「波導防護」、中文說明「受到接觸類物理招式的傷害減半」、英文說明 `Halves damage from physical contact moves`。

特性表的索引是按「產生過程中首次遇到」的順序配發的。鋒銳目前的首次使用者是 475 號的艾路雷朵，而阿勃梭魯是 359 號，因此阿勃梭魯Ｚ 會搶下較前面的位置；波導防護在 448 號插入又位移一次。**整張特性表因此重新編號，資料檔的差異會遠大於三個形態。**

這是無害的，因為特性表與所有引用它的形態是同一次產生的，而載入期的越界檢查會擋住來自不同產生批次的組合。但它有一個實務後果要寫進任務：**不可以手動比對特性索引來驗證正確性**，驗證要以特性名稱進行。

## Implementation Contract

**行為**：圖鑑分頁裡阿勃梭魯、烈咬陸鯊、路卡利歐三個物種的詳情面板，各多出一顆 MEGA 形態按鈕，選取後顯示該形態的屬性、種族值、特性與精靈圖，而學習集表格的內容與選取一般 MEGA 時完全相同。

**資料形狀**：三筆新形態進入資料集後應具備下列欄位值。`si` 一律為 0，即與物種既有的唯一一段學習集共用。

| 欄位 | 超級阿勃梭魯Ｚ | 超級烈咬陸鯊Ｚ | 超級路卡利歐Ｚ |
|---|---|---|---|
| 英文形態名 | `Mega Absol Z` | `Mega Garchomp Z` | `Mega Lucario Z` |
| 中文形態名 | 超級阿勃梭魯Ｚ | 超級烈咬陸鯊Ｚ | 超級路卡利歐Ｚ |
| 形態種類 | `mega` | `mega` | `mega` |
| 屬性 | `["Dark","Ghost"]` | `["Dragon"]` | `["Fighting","Steel"]` |
| 精靈圖 | `10307.png` | `10309.png` | `10310.png` |
| 種族值 | `[65,154,60,75,60,151]` | `[108,130,85,141,85,151]` | `[70,100,70,164,70,151]` |
| 特性 | 鋒銳 Sharpness | 飄浮 Levitate | 波導防護 Aura Guard |
| 學習集指標 | `0` | `0` | `0` |

三者的種族值總和分別為 565、700、625，與各自的一般 MEGA 相同。

**不變式的期望值**：物種 208、形態總數 363、MEGA 形態 78、地區形態 16、招式 496、招式參照 13928、特性 201、有中文名的特性 199、有中文說明的特性 182、有英文說明的特性 201。這十個數字必須同時出現在資料集的統計區塊與 `src/data/dex.ts` 的載入期期望值，兩者不一致時載入即拋錯。

**失效模式**：

- 中文名推導未涵蓋 Z：不會拋錯，形態切換器出現兩顆同名按鈕。這是本變更唯一的安靜失效，驗收必須直接比對推導輸出
- 名單解析仍吃進註解資料：物種數斷言在資料組裝階段拋錯，訊息會誤指為名單輪替
- 特性缺漏：資料組裝階段的特性斷言拋錯，訊息指出是哪個物種的哪個形態
- 精靈圖無法驗證：精靈圖驗證階段將該形態列為無可用圖片並拋錯

**驗收條件**：

- 重跑 pipeline 後，`src/data/dex.json` 與 `design/champions-dex.json` 兩份檔案都含有上表三筆形態，且兩份的內容互為等價（一份緊湊、一份縮排）
- 連續重跑兩次 pipeline，兩次產出的資料檔逐位元組相同
- `pnpm test` 全數通過，含更新後的資料集不變式測試
- `pnpm run typecheck` 通過
- `pnpm run check` 的每一項回報 ok
- 三個物種的中文形態名各自互不相同，且第二顆 MEGA 按鈕的文字以全形Ｚ 結尾
- 實機確認三個新形態各自畫得出來：精靈圖載入、屬性標記正確（阿勃梭魯Ｚ 是本資料集裡阿勃梭魯第一次帶兩個屬性）、種族值長條與特性說明可讀，其中波導防護的中文說明是本次新寫的字串。**版面本身不是風險**：兩顆 MEGA 按鈕的排法噴火龍與雷丘早就在用，而「超級阿勃梭魯Ｚ」7 字並未超過既有最長的形態名（「超級麻麻鰻魚王」同為 7 字，肯泰羅的「帕底亞的樣子（鬥戰種）」11 字）

**範圍邊界**：

- 在範圍內：`design/pipeline/` 的名單解析、中文名推導、資料組裝與新增的 overlay；重新產生的資料檔；載入期期望值；資料集不變式測試；`dex-data` 與 `dex-query` 兩份規格；`ROADMAP.md` 的待收清單
- 在範圍外：任何 `src/components/` 底下的元件；任何樣式檔；`src/data/i18n.ts` 的字串表；招式與招式旗標相關的一切；五筆缺學習集的上游資料

## Risks / Trade-offs

- **中文名推導規則的既有驗證涵蓋不到 Z，寫錯會安靜通過** → 驗收以實際推導輸出比對三個名稱互不相同，而非依賴既有斷言
- **特性表整體重新編號，資料檔差異遠大於變更本身，令人誤以為出錯** → 在設計與任務中寫明此為預期行為，且驗證一律以特性名稱而非索引進行
- **overlay 是手寫資料，而本專案的既有規範是資料集不得手改** → overlay 位於 pipeline 輸入側而非產物側，產物仍然完全由重跑產生；每一筆均註明出處與「上游補齊後應刪除」的條件
- **上游日後正式上線這三個形態時，overlay 與上游會同時供應同一筆資料** → 名單解析剝除註解後，上游正式列會與 overlay 產生重複的形態；解除方式是刪除 overlay 並重跑，以產出是否不變來驗證等價
- **烈咬陸鯊Ｚ 的單屬性龍取自上游一行註解掉的、尚未定稿的資料** → 該形態的特性是飄浮，與失去地面屬性互相印證，兩者一致；若上游定稿後改變，屬性與特性應一併重新檢視
- **五筆缺學習集的上游資料在下次對照時可能被當成新發現重新提出** → 記入 `ROADMAP.md` 並寫明做不了的原因與重新評估的條件

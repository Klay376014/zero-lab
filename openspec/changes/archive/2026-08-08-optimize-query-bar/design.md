## Context

查詢列（`src/components/QueryBar.vue`）目前是四列：搜尋、屬性、世代、排序。在 390×844 的手機上，從 `.Root` 的 `height: 100vh` 往下推，padding 鏈為 12 → 9 → 12，內容寬 324px：

| 區塊 | 估計高 | 來源 |
| --- | --- | --- |
| Masthead | 約 145px | 標題、Sub／模式／語系列、Tally 四格 |
| 搜尋列 | 約 30px | 標籤 + 輸入框 + 清除鈕 |
| 屬性列 | 約 56px | 18 顆 × 25px 寬，(324−32)/25 = 11 顆一行，換行成 11 + 7 |
| 世代列 | 約 54px | 9 顆 × 33px 寬，8 顆一行，換行成 8 + 1 |
| 排序列 | 約 30px | 兩顆鈕承載一個二值選擇 |
| 查詢列邊框與間距 | 約 16px | |
| **剩給 DexGrid** | **約 447px** | |

卡片高約 181px（96px 圖 + 頭尾文字 + padding + 儲格 padding），所以一次看得到約 2.5 列。

三項既有的平台事實約束這個設計：

- `App.css` 零處使用 CSS grid（`design/HANDOFF.md` §12.16），欄位對齊一律以 flex + 寬度達成。
- 平台的 box model 把 padding 算在宣告寬度內，這正是 `.DexCell` 用百分比寬 + padding 當間隙的原因，該檔案的註解已記載。
- 在 web 預覽量到的文字寬度、換行位置與截斷與否**全部是錯的**，因為像素字面在 shadow root 內不載入（§12.5、§12.17）。任何與文字寬度有關的判斷只有實機或依 §12.17 注入字型後才算數。

`dex-query` spec 只約束查詢的狀態與行為，對呈現零約束 —— 沒有任何一條規定標籤存在、也沒有規定排序要露出幾顆控制項。`press-feedback` spec 第 148 條則明列了控制項清單，其中含「every generation filter button」與「every sort button」。

## Goals / Non-Goals

**Goals:**

- 查詢列高度由約 186px 降至約 114px，網格由約 447px 增為約 519px（可見卡片約 2.5 列 → 約 2.87 列）
- 屬性晶片固定九顆一排、兩排欄位對齊、寬度平均分配
- 屬性晶片的觸控目標由 22×22 放大
- 移除世代篩選，且不留任何替代控制項

**Non-Goals:**

- **不動 Masthead 的 Tally 四格。** 那是第二大的可回收區塊（約 41px），但 `dataset-statements` spec 有「The masthead SHALL state four counts」需求加 scenario 加 example，移除它是「資料集聲明放哪裡」的問題，不是查詢列的問題，應為獨立的 change。
- **不移除搜尋語料的 `gen<n>` token。** 見下方決策。
- **不把屬性列做成折疊式。** 折疊可再省約 56px，但屬性篩選是搜尋之外最常用的控制項，把它藏在一次點擊之後，省下的空間換的是每次篩選多一次操作。
- **不把屬性列做成水平捲動。** 可再省約 25px，但垂直捲動的網格上方疊一個水平捲動區是手勢衝突，且巢狀捲動在本平台只對「同向」量過（§12.19），異向未量。
- **不改屬性篩選的單選語意。** `ROADMAP.md` A4 記的多選縮減不在本次範圍。
- **不加第三種排序。** `ROADMAP.md` A6 的名稱排序不在本次範圍，但本設計對它有影響，見風險段。

## Decisions

### 移除世代篩選，搜尋語料的 gen 世代 token 保留

世代篩選整個移除：`src/state/query.ts` 的 `genFilter` ref、`matchesGen` 判定、`resetQuery` 中重設它的那一行、匯出清單中的它，以及 `src/components/QueryBar.vue` 中整列控制項與 `pickGen`，還有 `src/data/i18n.ts` 中 `gen` 這個標籤鍵與其介面欄位。

`src/data/i18n.ts` 的 `GEN_ROMAN` 與 `genOfLabel` **不動** —— 卡片與詳情面板在用它們顯示世代，與篩選無關。

搜尋語料中形如 `gen` 加數字的 token **保留**。它不是為了當世代的替代入口而留：`dex-query` 現行 haystack 需求把它與物種名、分類、編號、形態標籤、屬性名列在同一句，並有實測值 `gen5` → 29 筆、`gen5 dragon` → 1 筆（Hydreigon）。移除它會刪掉一段有自己論證與量測的 spec 內容，屬於獨立的行為縮減，不該搭這班車。它留著不佔畫面、不對應任何控制項，使用者不知道也不受影響。

需要改寫的是它的**理由**：現行 spec 說 haystack 帶的是「placeholder 點名的四件事，加上隨它們而來的分類與世代」，其中「世代」原本與世代篩選對稱；改後它成為純搜尋能力，spec 必須說出這件事，否則下一個讀者會以為那是遺留物而刪掉它。

替代方案：連 token 一起移除。否決，理由如上 —— 那是另一個 change 的內容。

### 排序改為單顆循環晶片並併入搜尋列

排序列整列移除，改為單顆晶片放在搜尋列，位置在輸入框之前。晶片文字即當前排序值（「編號」或「種族值」），按一下在兩者之間循環。

`dex-query` spec 對排序的約束是「a closed set containing at least national number and base-stat total」，講的是集合成員，不約束呈現。所以以單顆循環晶片承載一個二元封閉集合不違反任何需求。

替代方案：保留兩顆鈕但把整列併到搜尋列尾端。否決 —— 兩顆鈕在中文下約 111px，搜尋列塞不下（見下一項的寬度計算）。

### 移除搜尋標籤而非縮短清除鈕

搜尋列改後有三個元素。以 13px 字、內容寬 324px 計：

| 版本 | 排序晶片 | 標籤 | 清除鈕 | 輸入框剩下 |
| --- | --- | --- | --- | --- |
| 保留標籤 | 59px | 32px | 72px | **161px** |
| 縮短清除鈕為「清除」 | 59px | 32px | 52px | **181px** |
| **移除標籤** | 59px | — | 72px | **213px** |

placeholder 是 `名稱 / 編號 / 屬性 / 形態`，13px 下約需 200px；英文的 `Name / no. / type / form` 約需 154px。只有第三種版本兩個語系都裝得下。

選擇移除標籤而非縮短清除鈕，理由是資訊量：placeholder 是畫面上唯一點名搜尋四種能力的地方，而 `dex-query` 的 haystack 需求原文就是靠它立論的 ——「These are the four things the search field's placeholder names — name, number, type, form」。截斷 placeholder 等於截斷那條需求的依據。相對地，一個帶 placeholder 的輸入框在畫面上只有一個，不需要另一個標籤說明它是什麼。

上表的寬度是從樣式表推算的，不是量的。實機驗證與退路見實作契約與風險段。

### 屬性晶片以百分比寬強制九顆一排

查詢列結構改為：標籤與晶片容器並排，晶片容器 `flex: 1` 且 `flex-wrap: wrap`，十八顆晶片各佔容器寬的 `11.111%`。九顆剛好 100%，所以斷點必然落在第九顆，兩排各九顆且欄位自動對齊。

沿用 `.DexCell` 已確立的三個要件：

1. 百分比寬 —— 平台把 padding 算在宣告寬度內，所以 `11.111%` 是含 padding 的總寬。
2. 間隙由 padding 給，不由 margin 給 —— margin 會落在百分比之外，把第九顆推到下一排。晶片現有的 `margin-right: 3px` 必須移除。
3. `flex-shrink: 0` —— 否則換行容器會壓縮成員以多塞一顆，把九顆一排變成十顆擠一排。

不用 `justify-content: space-between`：那個做法讓晶片保持 22px 方形、把空白分配到間隙，但兩排都是九顆時視覺結果與百分比寬相近，而百分比寬同時達成觸控目標放大（下一項），且不必依賴 space-between 與 margin 的交互作用。`justify-content` 本身在本平台有實據（§12.16 的覆蓋層置中在用）。

不用 CSS grid：`App.css` 零處 grid（§12.16），本次不引入。

### 屬性晶片的觸控目標放大

晶片寬由 22px 變為約 32.4px（`11.111%` × 292px 可用寬）。垂直 padding 由 2px 提至 5px，晶片高由 22px 變為約 28px（16px 字符 + 10px padding + 2px 邊框）。

字符本身維持 16px —— `type-glyph` spec 要求固定十六像素盒且只以整數倍縮放，本次不縮放它，晶片變大是 padding 變大，字符在其中置中。

代價是屬性列由約 50px 變為約 62px，總回收由 84px 降為約 72px。仍達成目標區間。22×22 是這條列上最嚴重的可觸及性缺陷，既然已在改寬度，一併處理。

### press-feedback 控制項清單同步

`press-feedback` spec 第五條需求逐一列舉哪些控制項帶按壓位移。清單中的「every generation filter button」隨控制項消失而移除；「every sort button」改為單顆排序循環鈕。新的排序晶片必須綁齊三個主執行緒觸控事件（start、end、cancel），與既有控制項一致 —— cancel 是讓變成捲動的按壓得以釋放的那一個。

## Implementation Contract

**In scope**：`src/state/query.ts`、`src/components/QueryBar.vue`、`src/data/i18n.ts`、`src/App.css` 的 controls 區段，以及 `openspec/specs/dex-query/spec.md` 與 `openspec/specs/press-feedback/spec.md` 的 delta，加上 `ROADMAP.md` 的三處條目更新。

**Out of scope**：Masthead 與 Tally、屬性篩選的單選語意、第三種排序、搜尋語料的內容、卡片與詳情面板的世代顯示、任何 `src/` 之外的執行期程式碼。

**行為契約（使用者可觀察到的）**

1. 查詢列只有兩列：第一列是排序晶片、搜尋輸入框、清除鈕；第二列是「屬性」標籤與十八顆屬性晶片排成兩排。畫面上不存在任何世代篩選控制項，也不存在寫著「搜尋」的標籤。
2. 排序晶片顯示當前排序值。按一下由「編號」變為「種族值」，再按一下變回「編號」。網格順序隨之改變，與現行兩顆鈕的結果完全相同。
3. 屬性晶片每排九顆、共兩排。第二排第 n 顆的左緣與第一排第 n 顆的左緣對齊。屬性列不橫向溢出。
4. 清除鈕把搜尋字串清空、屬性篩選清掉、排序回到「編號」。世代不再是它要重設的東西。
5. 在搜尋框輸入 `gen5` 仍得到 29 筆，`gen5 dragon` 仍得到 1 筆 —— 這條能力未受本次變更影響。
6. 屬性晶片、排序晶片、清除鈕按下時都有一像素向下位移，放開或按壓被取消時位移消失。

**狀態契約**

`src/state/query.ts` 對外匯出的查詢狀態由四項變為三項：搜尋字串、屬性篩選、排序順序。`genFilter` 不再存在，`matchesGen` 不再存在。結果序列的形狀（每個元素帶一個物種與一個形態索引）不變。

**失敗模式**

沒有新的錯誤路徑。唯一的失效可能是靜默的版面失效，形態是 §12.17 記的那一類：宣告寫得下去、不報錯、行為沒發生。具體有兩種 ——

- 屬性晶片變成每排八顆或十顆：代表百分比寬、padding 間隙、`flex-shrink: 0` 三個要件有一個沒到位。判別方式是數畫面上第一排的晶片數，不是看樣式表。
- placeholder 被截斷：代表輸入框實際寬度小於推算值。

**驗收條件**

- 執行 pnpm run check，四項不變式全數通過（非零退出即失敗）
- 執行 TypeScript 型別檢查（對 `src/tsconfig.json` 做 noEmit），零錯誤。移除 `genFilter` 之後任何殘留的引用都會在這裡現形
- `spectra validate optimize-query-bar` 通過
- 實機（或依 §12.17 注入字型後的 web）確認：屬性列每排九顆、兩排左緣對齊、placeholder 兩個語系都不截斷
- 逐項對照上面六條行為契約

## Risks / Trade-offs

**[placeholder 在實機上仍被截斷] → 退路已定義**：把「搜尋」標籤放回來，並把排序晶片退回自己一列。結果是只省約 54px（僅移除世代列），網格約 501px，可見卡片約 2.77 列。這個退路要連同 spec delta 一起回退排序與標籤的部分，世代的移除不受影響。判定必須在實機或注入字型後進行 —— §12.5 與 §12.17 已確立 web 預覽量到的文字寬度是錯的。

**[屬性晶片變成 32×28 的長方形，不再是方塊] → 接受**：這是「平均分配整排寬度」的直接結果，也是觸控目標放大的來源。若視覺上不可接受，替代做法是改用 `justify-content: space-between` 保持 22×22 方形，但那會放棄觸控目標的改善。

**[排序循環晶片與 ROADMAP A6 的第三種排序衝突] → 已記錄**：循環在二元集合上成立，在三元集合上會開始難用（要按兩下才到得了最後一項，且看不見有幾個選項）。A6 若要做，排序控制項應改為可展開的選單而非循環。這一點要寫進 `ROADMAP.md` 的 A6 條目，讓下一個提案者不必重新發現。

**[移除「搜尋」標籤降低可及性] → 已知且未惡化**：`ROADMAP.md` 記載移植版目前零 a11y 屬性，所以沒有 accessibilityLabel 會因此失效。但這使得輸入框在畫面上與語意上都只剩 placeholder 承載其身分。當 a11y 那一項被處理時，這個輸入框需要一個 accessibilityLabel —— 這一點要寫進 `ROADMAP.md` 的 a11y 條目。

**[世代維度從此無控制項入口] → 使用者已明確確認**：討論中確認不需要世代作為入口。搜尋 token 仍在，但它不會被使用者發現，也不宣稱是替代品。若日後判定需要，重新加回的成本是 `query.ts` 一個 ref 加一個判定、`QueryBar.vue` 一列、i18n 一個鍵，加上兩份 spec 的 delta。

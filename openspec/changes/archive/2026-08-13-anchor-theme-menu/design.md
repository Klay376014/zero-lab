## Context

主題選單目前是 root 的 overlay band 裡一塊絕對定位的面板，位移寫死在樣式表（左 21、上 21，即機身 9 + 螢幕 12）。這個排列來自兩個當時成立的限制：

- `design/HANDOFF.md` §12.28 —— `SelectorQuery.fields({ rect: true }, cb)` 的 callback 在 web 預覽與 iOS 實機都不回，所以沒有辦法知道觸發鈕在哪。跟隨 anchor 的定位程式碼曾經寫過並被移除。
- `design/theme-menu-variants.html` —— 變體 C（掛在鈕下方）要靠 `z-index`，而當時 `src/App.css` 全檔零處 `z-index`，平台也沒量過，被記為「押未量測行為」。

2026-08-13 的實機探針結清了第二點。§12.29 量到：`z-index` 在本平台成立，且一塊掛在 masthead row 下方、`z-index: 10` 的面板確實蓋過 `Screen` 內後續的 QueryBar，連 masthead 的 3px 下框一起蓋過去 —— 既不是被裁切也不是被蓋。第一點沒有改變，`fields` 仍然不回 callback，但錨定做法根本不需要它。

§12.29 量到的疊層是「masthead 內的節點越過 `Masthead` 與 `Screen` 兩層，蓋住 `Screen` 內的後續兄弟」。**關閉用的攔截層比這高一層**（它是 `Root` 的直接子節點），所以選單與攔截層的相對順序不在已量範圍內 —— 這是本次唯一需要在實機上額外確認的疊層關係。

## Goals / Non-Goals

**Goals:**

- 選單開在觸發鈕正下方，且位置不由任何執行期量測或座標運算決定，只由版面決定。
- 按壓回饋（`press-feedback`）與選單位置互不影響：按住觸發鈕時選單不得跟著位移。
- 選單與攔截層的上下關係由宣告的數值決定，而不是由誰在子樹的哪個位置決定；若該關係在實機上不成立，有一條已寫明的退路，而不是留下一個按了沒反應的控制項。
- 錨定所需的樣式以「wrapper 類別 + 面板類別」的組合表達，未來其他控制項套用同一組類別即可，不需要複製定位邏輯。

**Non-Goals:**

- 不做 `ROADMAP.md` A6 的兩個排序控制項。
- 不把錨定選單抽成獨立的 capability spec 或獨立元件 —— 只有一個消費者，第二個的行為還沒被決定。
- 不改用觸控事件座標定位（§12.29 第一條）。
- 不重拍 `design/theme-menu-variants.html` 的截圖。
- 不改按壓回饋的控制項清單或位移量。
- 不處理選單超出螢幕右緣的水平夾制（見 Risks）。

## Decisions

### 觸發鈕外包一層不綁按壓事件的 wrapper 當 containing block

選單的 containing block 是**新增的一層 wrapper**，不是觸發鈕本身。

觸發鈕帶著 `press-feedback` 的主線程函式，按下時寫入 `transform: translateY(1px)`。若選單以觸發鈕為 containing block，會有兩個後果：按住鈕的時候選單跟著往下抖一格；而且 `transform` 在 CSS 規範裡會替後代的絕對定位元素另外產生 containing block，Lynx 是否照做**沒有量過**——那會讓選單的位置取決於一個未驗證的行為。

wrapper 不綁任何觸控事件，兩件事因此完全不相干。代價是 masthead row 多一層節點。

考慮過的替代：把 `position: relative` 直接加在觸發鈕上（省一層節點，但上述兩個後果都會發生）；把位移量從主線程搬掉讓觸發鈕不再有 transform（那要動 `press-feedback` 的既有結論，而 §12.22 第四條說明了位移量為什麼非在主線程的字面值不可）。

### 攔截層以宣告的 z-index 排在選單之下，並保留移除攔截層的退路

選單宣告 `z-index: 10`，攔截層宣告 `z-index: 1`。兩者的上下關係因此由數值決定，而不是由「誰是誰的後續兄弟」決定。

需要這樣做的原因是子樹位置反過來了。現在選單與攔截層同在 overlay band，攔截層排在前面所以選單畫在上面；改成錨定之後，選單在 masthead 內、攔截層仍在 `Root` 的直接子層，**攔截層變成後續節點**。若不宣告順序，攔截層會蓋在選單上 —— 而攔截層雖然不畫任何顏色（不宣告背景色，POCKET 的四色契約不受影響），它仍然會收觸控，結果是按選單列變成關閉選單，一列都選不到。

這一層關係比 §12.29 量到的高一階，所以它是本次的實機驗收項目。**退路**：若實機上攔截層仍然吃掉選單的按壓，則移除攔截層，只留觸發鈕再按一次關閉 —— `theme-menu` 現行 spec 已經要求觸發鈕本身必須足以關閉選單，也已經寫明「若攔截層被量到無效就移除，不要留著一條沒有作用的宣告」。退路不需要新的規格授權。

考慮過的替代：把攔截層改掛到 masthead 內選單的前面（那樣它就蓋不住整個螢幕，失去存在的意義）。

### 選單以 top 100% 對齊觸發鈕左緣，不做水平夾制

選單 `position: absolute`、`left: 0`、`top: 100%`。`left: 0` 對齊 wrapper 的左緣也就是觸發鈕的左緣，`top: 100%` 落在觸發鈕下緣。兩個值都是版面關係，不是量出來的常數 —— 這是與現行做法最重要的差別：現行的 21px 是兩個 padding 相加的字面值，觸發鈕的水平位置其實在結果計數之後，寬度隨數字與語言改變，所以那個值從來就對不準它想指的東西。

不做水平夾制（不偵測是否超出螢幕右緣再翻邊）。三個模式名稱都很短，而**在本平台量文字寬度是不可靠的**：`fields` 不回 callback，web 預覽又因為像素字型不載入而把拉丁字的寬度量錯（`design/HANDOFF.md` §12 開頭）。夾制若做，只能靠猜的常數，那與現行做法的毛病是同一個。超出時的處置寫在 Risks。

### 錨定形狀以類別組合表達，不抽成獨立元件

錨定所需的東西是兩條規則：wrapper 的 `position: relative`，面板的 `position: absolute` + `top: 100%` + `z-index`。這兩條以獨立、不帶主題語意的類別名稱存在於樣式表，`ThemeMenu.vue` 套用它們。

不包成 `<AnchoredMenu>` 之類的元件：目前只有一個消費者，而第二、第三個消費者（A6 的兩個排序控制項）連自己的行為都還沒定案 —— 現在抽象等於替還沒被決定的東西定介面。類別組合已經足以讓下一個消費者不必重寫定位邏輯，而抽元件這件事在有兩個真實消費者時再做，成本不會比現在高。

## Implementation Contract

**Behavior**

按下主題選單觸發鈕時，選單出現在該鈕的正下方、左緣與該鈕左緣對齊，覆蓋其下方的介面（屬性篩選列所在的區域）。再按一次觸發鈕關閉。選擇任一列設定模式並關閉選單。這些行為在三個模式、兩種語言、以及任何結果筆數下都相同 —— 選單位置不隨結果計數的字寬改變，因為它不再由字面常數決定。

按住觸發鈕時，觸發鈕本身下移一格（既有的按壓回饋），**選單不動**。

**Structure / interface**

- `ThemeMenu.vue` 的根節點成為一層不帶按壓綁定的 wrapper，內含既有的觸發鈕與（開啟時）選單面板。選單面板因此由 `ThemeMenu.vue` 渲染，不再由 `App.vue` 的 overlay band 渲染。
- `App.vue` 不再直接渲染選單面板，也不再匯入選單列元件；攔截層仍留在 root 的 overlay band，因為它必須蓋住整個螢幕。
- 樣式表新增兩件事：wrapper 的定位規則，以及面板由固定位移改為錨定位移並宣告 stacking 值。攔截層宣告一個低於面板的 stacking 值。
- `ThemeMenuList.vue` 的行為不變（仍由呼叫端傳入定位類別），但其檔頭說明目前描述的是 overlay band 的排列，要改為描述錨定排列。

**Failure modes**

- 攔截層若在實機上吃掉選單列的按壓（表現為：按任一列都只是關閉選單、模式沒有改變），移除攔截層，只保留觸發鈕再按一次關閉。這是已授權的退路，不需要改規格。
- `z-index` 若在實機上不生效（表現為：選單被屬性篩選列蓋住），整個變更回退到現行的 overlay band 排列。此情況與 §12.29 的量測矛盾，回退前先重跑 §12.29 的重建條件。
- 選單若被祖先節點裁切（表現為：選單在 masthead 下緣被一刀切齊、篩選列完全正常），同上回退。§12.29 已排除這一項，列在這裡是為了讓驗收的人知道要分辨「被蓋」與「被裁」——判法是看誰的邊緣是直的。

**Acceptance criteria**

- pnpm run check 通過。新增的 stacking 宣告不得觸發既有的四項不變式（本次不新增選取態規則、不新增 inset 陰影、不新增散文字元、不新增 GlyphSurface 成員）。
- pnpm run typecheck 通過（vue-tsc，不是 tsc）。
- pnpm test 通過且測項總數不變（253）。本次不改任何 Example 表 —— 選單位置在 Node 裡量不到，`tests/theme.test.ts` 覆蓋的是模式集合與開關狀態，兩者都不動。
- iOS 實機驗收，四項：選單開在觸發鈕正下方且完整可讀；按住觸發鈕時鈕下移而選單不動；按選單列會換模式而不是只把選單關掉（這是攔截層那一項）；篩選結果縮到個位數後再開一次，選單仍在鈕的正下方。
- web 預覽不作為判準。§12.29 與 §12.22 都記過同一件事：web 跑的是瀏覽器的實作。

**Scope boundaries**

在範圍內：`ThemeMenu.vue` 的結構、`ThemeMenuList.vue` 的檔頭說明、`App.vue` 的 overlay band 內容與匯入、`App.css` 的選單相關規則、`theme-menu` spec 第三與第四條 requirement、`design/theme-menu-variants.html` 的結論文字。

在範圍外：A6 的排序控制項、觸控座標定位、`press-feedback` 的任何行為、`design/theme-menu-variants.html` 的截圖、水平夾制、新增檢查腳本。

## Risks / Trade-offs

- **攔截層與選單的疊層關係比 §12.29 量到的高一層，可能不成立** → 退路已寫明且已被現行 spec 授權（移除攔截層，觸發鈕獨力關閉）。這是本次唯一沒有事前量測就下的賭注，而它的失敗是可見的（按列沒反應），不是無聲的。
- **選單超出螢幕右緣** → 三個現有模式名稱（POCKET / MODERN / EMERALD）都短，觸發鈕位在 masthead row 中段，目前不會發生。若日後某個模式名稱長到溢出，處置是把面板的 `left: 0` 改為 `right: 0` 讓它向左展開 —— 一行改動，且同樣不需要量測。**不預先做**：現在做等於為猜測中的名稱長度寫程式。
- **masthead row 多一層節點** → §12.24 記過 `<svg content>` 的光柵化成本按元素計價，但那是 svg 專屬的；wrapper 是一個不畫任何東西的 view，且在 masthead 只有一個實例，不在任何長序列裡。
- **`src/App.css` 首次出現 `z-index`** → 現行 `theme-menu` spec 明文寫著不得引入 stacking index，理由是「其效果在本平台未量測」。該理由已經失效（§12.29），所以改寫的是 requirement 而不是繞過它。但要注意已量範圍僅止於此：跨 `<scroll-view>` 邊界與更深的巢狀都沒有量，本次也不依賴那些。

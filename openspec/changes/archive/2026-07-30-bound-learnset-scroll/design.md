## Context

詳情面板目前的結構是：標題列在捲動容器外，`DetailBody` 是唯一的捲動容器且高度固定 `60vh`，裡面依序是大圖舞台、四項屬性、警語、種族值、特性、招式表。招式表沒有高度上限，105 列（艾路雷朵 #475）全部展開。

這是移植時刻意的取捨，理由記在 `design/HANDOFF.md` §12.16 兩列：巢狀同向捲動會搶同一個手勢。付出的代價同樣記在那裡 —— 面板由內容決定高度，長內容就是長內容。本變更判定那個代價不值得：招式表是面板裡最需要來回比較的一段，卻被排在最後、要捲過約 500px 的其他內容才到得了。

三個既有限制決定了做法：

1. **`<scroll-view>` 沒有巢狀捲動的仲裁屬性。** 官方屬性表只有 `bounces`、`enable-scroll`、`scroll-orientation`、`initial-scroll-offset`、`initial-scroll-to-index`、`upper-threshold`、`lower-threshold`、`scroll-bar-enable`。`enable-nested-scroll`（預設 `true`、內層先捲）是 `<list>` 的屬性。所以兩層垂直捲動誰吃手勢在本平台**沒有可設定的旋鈕，也沒有實測結果**
2. **`<list>` 不能用。** §12.13：vue-lynx 只實作尾端追加，`removeAction` 與 `updateAction` 硬編為空陣列。招式表有三種排序與本系篩選，序列會變動
3. **只有 `max-height` 的捲動容器不會捲。** §12.16 已記過這個失敗模式兩次：捲動容器需要可解析的確定高度，否則長到內容高度、什麼都不捲

## Goals / Non-Goals

**Goals:**

- 招式表長到超過一個可讀視窗時，自己捲，面板不再被它拉長
- 欄位表頭在招式表捲動時留在原地 —— 否則捲到第 50 列時六個欄位沒有標籤
- 招式表短的時候不出現空白框
- 巢狀捲動一旦在實機上打起來，有寫好的退路可換，不必回頭重新設計

**Non-Goals:**

- 不動 `dex-grid` 對網格的同名禁令 —— 網格不在面板裡
- 不動面板自身的 `60vh` 捲動區
- 不改招式表的欄寬、三種排序、本系篩選、單列截斷與星號
- 不用 `<list>` 實作內層
- 不重新引入 sticky
- 不為「面板內的捲動容器數量」加機械檢查（理由見下）
- Android 不驗

## Decisions

### 招式表的捲動區只在真的需要時才有界

招式表根節點永遠是 `<scroll-view>`，但**確定高度只在列數超過門檻時才套用**。列數少於門檻時不套高度，容器長到內容高度、什麼都不捲 —— 等於沒有第二層捲動。

**為什麼不永遠有界**：變隱怪只有 1 招。一個固定高度的框在它身上會是一個約 290px 的空白方框卡在特性與面板底部之間，看起來像壞掉。面板底部的空白（§12.16 已接受的代價）在視覺上是「面板結束了」，中段的空白方框不是。

**為什麼不用 `max-height`**：限制 2 —— 只有 `max-height` 的捲動容器不會捲。這個失敗模式在本專案已經踩過兩次，不要踩第三次。

**替代方案（已否決）**：用 `<component :is>` 在 `scroll-view` 與 `view` 之間切換，讓不需要捲的情況連容器都沒有。否決理由是 vue-lynx 對內建元素標籤的動態解析沒有實測過，而它換到的東西只是元素樹乾淨一點。

門檻與高度必須一致：門檻 = 該高度在最小目標裝置上容得下的資料列數。

### 高度用視窗比例而非設計稿的 400px

設計稿是 `max-height: 400px`，那是為不窄於 500px 的瀏覽器調的。面板的捲動區是 `height: 60vh`，在 667px 高的裝置上是 400px —— 照抄字面值會讓招式表**吃掉整個面板可見區**，面板變成只有招式表。

改用 `36vh`。兩個上下界決定這個值：

| 界線 | 條件 | 在 667px 高的裝置上 |
|---|---|---|
| 下界 | 表頭之外至少要看得到 8 列資料 | 36vh = 240px，資料列約 22px（12px 字 + 上下 3px + 1px 框線）→ 約 10 列 |
| 上界 | 不得超過面板捲動區的三分之二，否則外層等於不能用 | 36vh / 60vh = 60% |

門檻因此定為 **12 列** —— 在 812px 高的裝置上 36vh = 292px 約容得下 13 列，取 12 列使「有界但不需要捲」這個中間狀態不會出現。

### 欄位表頭移到內層捲動容器之外

表頭現在是流內的第一列（`MoveHead`），理由寫在原始碼註解裡：這張表沒有自己的捲動區可以黏。現在有了，所以它必須移出去 —— 這不是順手改進，是內層捲動帶來的義務。

做法沿用面板標題列：放在捲動容器**外面**，不用 sticky（§12.15 已確立這個做法成立，也不必賭平台支不支援 sticky）。

欄位對齊不受影響：表頭與資料列共用同一組欄位 class（`MoveGlyphCell` / `MoveName` / `MoveClass` / `MoveFigure` / `MoveFigurePp`），而共用 class 正是對齊的來源。**但捲軸會破壞它** —— 資料列在捲動容器內、表頭在外，若平台為捲動容器保留捲軸寬度，兩者的右緣會差一個捲軸。驗收條件因此包含「表頭與資料列六欄左緣一致」，退路是關掉 `scroll-bar-enable`。

### 巢狀同向捲動的手勢仲裁必須實機驗收，並預先寫下退路

`<scroll-view>` 沒有 `enable-nested-scroll`，所以三種行為都可能：內層先捲（想要的）、外層吃掉手勢（招式表捲不動）、或手勢在兩層之間跳動。**web 預覽答不了這件事** —— 它跑的是瀏覽器的捲動實作，不是 native 的手勢鏈。

實機要驗三件事：手指在招式表上時捲的是招式表；招式表捲到底之後繼續往上滑會不會接手到外層（接手最好，不接手可接受）；手指在招式表**之外**時捲的是面板。

退路依序：

1. **首選 —— 招式表改為可收合**：預設收起，標題列已經有列數（`LearnsetCount`），點一下展開。這解掉原本的問題（面板不再被招式表拉長）而**完全不需要巢狀捲動**。代價是多一次點擊
2. **次選 —— 關閉外層在招式表區域的拖曳**：`enable-scroll` 是布林、不分區域，所以這條只有在能以「手指是否在表上」切換外層 `enable-scroll` 時成立，需要額外驗證
3. **末路 —— 還原**：拿掉高度與內層捲動，把「已實測不成立」寫進 §12，並把這一項移回 `ROADMAP.md` 的 C 節

退路 1 不需要新的平台事實，所以它是真的退路而不是另一個賭注。

### 不為「面板內的捲動容器數量」加機械檢查

`pnpm run check` 的兩支腳本讀的是樣式表與主題原始碼。捲動容器的數量是**模板**的性質，兩支腳本都看不到。要檢查得剖 `.vue` 模板，那是一套新工具。

不做的理由是失敗模式不同：這件事壞掉的症狀是**捲不動**，一眼看得出來，不像字符消失或選中狀態被自己的基底規則取消那樣靜默。`pnpm run check` 存在的目的是抓靜默失效，這一項不屬於那一類。

## Implementation Contract

**Behavior**

- 招式表列數超過 12 時：招式表自己捲，高度為 `36vh`；面板其餘內容不再被它推長
- 招式表列數為 12 或更少時：不套高度、沒有內層捲動，行為與現在完全相同
- 欄位表頭在招式表捲動時不動，且與資料列的六欄左緣一致
- 本系篩選把列數壓到 12 以下時，界線隨即消失（門檻看的是**當前顯示的列數**，不是該物種的招式總數）

**Interface / data shape**

- `LearnsetTable.vue` 的根節點下多一層：控制列與欄位表頭在捲動容器外，資料列與空結果訊息在內
- 內層容器是 `<scroll-view scroll-orientation="vertical">`，確定高度以 class 切換（不用 inline `:style`；§12.14 的結論是綁在自己寫的元素上才確定落點，而 class 與 `:class` 併用已確立可行）
- 門檻常數與高度值必須寫在一起並註明彼此的關係 —— 改一個不改另一個會讓「有界但不需要捲」這個狀態出現
- 樣式表新增的規則名沿用既有前綴（`Move*` / `Learnset*`）

**Failure modes**

- 手勢仲裁不如預期：**不是靜默失效**，招式表捲不動或面板捲不動當場看得出來。處理方式是切到上面的退路，不是調參數
- 捲軸佔寬導致表頭與資料列右緣不齊：關閉內層 `scroll-bar-enable`
- 列數恰在門檻附近來回（篩選開關）：容器有界與無界之間切換，這是預期行為，不是抖動

**Acceptance criteria**

| # | 條件 | 怎麼驗 |
|---|---|---|
| 1 | 艾路雷朵 #475（105 列）的招式表自己捲，面板高度不再由它決定 | iOS 實機 |
| 2 | 手指在招式表上捲的是招式表；在招式表之外捲的是面板 | iOS 實機 —— **這是本變更的核心未知** |
| 3 | 欄位表頭在招式表捲動時留在原地 | iOS 實機 |
| 4 | 表頭與資料列六欄左緣一致 | web 量 DOM（量的是固定欄寬的位置，不受字型影響，§12.17 已確立這類量測在 web 上成立） |
| 5 | 變隱怪 #132（1 列）沒有空白框，且面板沒有內層捲動 | web + iOS 實機 |
| 6 | 本系篩選把列數壓到 12 以下時界線消失 | web |
| 7 | `pnpm run check` 與 `tsc --noEmit` 仍通過 | 指令 |

第 2 項是唯一可能推翻整個做法的一項。**它答不出來之前，不要把 HANDOFF 的 §12.16 改成完成式。**

**Scope boundaries**

- 在範圍內：`LearnsetTable.vue` 的模板結構、`App.css` 的招式表區段、`species-detail` 與 `learnset-table` 兩份 spec、`design/HANDOFF.md` §12.16 對應兩列與新增一節平台事實、`ROADMAP.md` 的 C 節
- 不在範圍內：面板的 `60vh`、`dex-grid` spec、招式表的欄寬與排序與篩選邏輯、`scripts/` 兩支檢查、任何 Android 事項

## Risks / Trade-offs

- **[外層吃掉手勢，招式表捲不動]** → 實機驗收第 2 項就是為它設的。命中就切退路 1（可收合），它不需要任何新的平台事實
- **[內層吃掉手勢，面板在招式表區域捲不動]** → 可接受但不理想：面板其餘區域仍可捲，且招式表捲到底之後可能接手。若連「表外可捲面板」都不成立，切退路 1
- **[捲軸寬度破壞欄位對齊]** → 驗收第 4 項擋住，修法是關閉 `scroll-bar-enable`
- **[門檻與高度不同步]** → 兩者寫在一起並註明關係。不同步的症狀是「有界但捲不動的框」，屬於可見而非靜默
- **[面板結構變複雜]** → 從「面板一層捲動」變成「面板一層 + 招式表一層」。這是本變更刻意買下的複雜度：換到的是招式表可讀。§12.16 那兩列的理由要改寫成「例外只給招式表」，而不是刪掉 —— 其他區段仍然不得自帶捲動區
- **[web 預覽驗不到最重要的那一項]** → 已經寫在驗收表裡。第 2 項標為核心未知，不是待辦

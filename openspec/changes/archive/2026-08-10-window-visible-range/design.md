## Context

`design/HANDOFF.md` §12.24 用五刀單變數對照量出成因：**平台按元素計價，約 1.3ms 一個，與那些元素是什麼無關**。
網路、圖片快取、屬性字符、文字塑形、主線程觸控綁定全部逐一排除；最後一刀把每列節點數從 8.5 砍到 4，
#475 艾路雷朵的等待從 897ms 掉到 285ms。

`src/` 有十五處 `v-for`，其中十二處是小的（屬性 1–2、排序鈕 3、種族值 6、特性 ≤3）。**只有三處是大的**：

| 位置 | 最大筆數 | 每項元素數 | 元素總數 |
|---|---|---|---|
| `DexGrid` 卡片 | 208 | ~20 | ~4000 |
| `MoveLearners` 列 | 225（中位數 15）| ~8 | ~1800 |
| `LearnsetTable` 列 | 105 | ~8.5 | ~890 |

三處都在自己的 `<scroll-view>` 內，而 `<scroll-view>` 不回收。

約束條件：

- **不得使用平台的 list 綁定。** §12.13 已確立它只實作尾端追加，且該結論於 2026-08-10 重新複驗仍成立。
  `dex-grid` 與 `learnset-table` 兩份 spec 都已明文禁止它，`dex-grid` 並禁止引入第三方虛擬捲動套件。
- **識別鍵不得改變。** `dex-grid` 要求卡片鍵由物種編號加形態索引組成、不得由位置推導；招式列以招式名為鍵。
- **`learnset-table` 已有一條要求正是視窗化最容易違反的**：每一列都必須可達、不得空白、不得把某招的名字
  配到另一招的數值。它直接成為本次的驗收判準。
- **不得寫存取捲動位置以「還原」畫面的程式。** ROADMAP C 節明文禁止（Vue 的更新本來就留著捲動位置）。
  本次要讀的是**當下的捲動位移以決定渲染哪一段**，與那條禁令的對象不同 —— 但兩者容易被混為一談，所以
  spec 要把差別寫清楚。
- 招式表與學習者清單都在詳情面板的捲動容器**內**（巢狀同向捲動，§12.19 已實測成立）。

## Goals / Non-Goals

**Goals:**

- 讓同時掛載的元素數**有界**，不隨資料集或篩選結果成長。
- 網格的可視卡約 **10 張**（雙欄，約 5 列），前後各加緩衝。
- 區間推導是**純函式**，可在 node 下驗證 —— 這是本次唯一不必靠實機的部分，要把它做滿。
- 捲動範圍（可捲動的總高度）與未視窗化時相同，使用者感受不到內容被截斷。

**Non-Goals:**

- **不改變名稱換行的行為。** 卡片改為等高是靠保留空間，不是靠截斷；`species-card` 的
  「Long names wrap rather than truncate」維持不變。
- **不減少每個項目的元素數。** §12.24 記的另一個槓桿（合併數值欄、去掉包裹用的 view）留給後續，
  它與本次正交、可疊加，但混在一起會讓驗收分不出哪一項有效。
- **不使用平台 list 綁定、不引入第三方虛擬捲動套件。** 兩者都被既有 spec 明文禁止。
- **不改變任何識別鍵、篩選、排序、本系加成的判定。** 本次只改「哪些項目被渲染」，不改「有哪些項目、順序為何」。
- **不動十二處小的 `v-for`。** 它們每處最多幾個元素，視窗化的固定成本比省下的多。
- **不處理記憶體數字。** ROADMAP B 節那一列的記憶體部分仍然缺基線，本次不補。

## Decisions

### 區間推導做成純函式，與平台與框架都無關

輸入是捲動位移、可視高度、單項高度、每列項目數、項目總數、緩衝屏數；輸出是起訖索引與上下佔位高度。
不讀任何全域狀態、不碰任何元素。**這讓本次最容易出錯的部分（邊界、夾住、序列變短）能在 node 下用表格驅動測試**，
而不是靠實機目視。

考慮過並否決：把推導寫在各元件內。三處會各自長出一份邊界處理，而邊界正是最容易錯的地方。

### 捲動位移的來源由實機探針裁決，探針帶對照組

**整個方案壓在「`<scroll-view>` 送得出可用的捲動位移」上，而 `design/HANDOFF.md` 全文沒有任何一節提到捲動事件。**

原始碼證據（讀 Pods）：`LynxScrollEventManager` 送出的事件帶 `scrollTop`／`scrollLeft`／`scrollHeight`／
`scrollWidth`／`deltaX`／`deltaY`／`isDragging`；`LynxUIScrollViewInternal` 的另一條路徑只帶 deltas；
且有 throttle 屬性。**但 §12.6 與 §12.13 兩次都是文件與出貨程式碼不一致，原始碼證據不等於裝置證據。**

探針要回答三件事，且每一件都要能與「我綁錯事件名」區分：

| 臂 | 問什麼 | 判準 |
|---|---|---|
| 對照組 | 一個必然會發生的事件（元素的 `@tap`）綁在同一個捲動容器上 | 有沒有觸發 —— 排除綁定寫法本身就錯 |
| 位移 | 捲動時把收到的 detail 逐欄印在畫面上 | 有沒有 `scrollTop`；只有 deltas 時要累加，兩者實作不同 |
| 頻率 | 從頂捲到底，記錄事件次數與最大位移間隔 | 間隔大於一屏就會出現空白，緩衝量要據此定 |

**位移臂若只給 deltas**，推導的輸入改為累加值，而累加會漂移 —— 屆時要多一條「捲到頂時歸零」的校正，
這是設計上的分岔，所以要在寫元件之前知道。

### 佔位用兩個 view 撐住捲動高度，不改捲動容器本身

區間之前與之後各放一個沒有子節點的 view，高度等於被略過的項目數乘單項高度。捲動容器與其屬性完全不動。
兩個空 view 的成本是兩個元素，相對於省下的數百個可以忽略。

考慮過並否決：改用 padding 或 transform 位移。前者在本平台未量過對捲動範圍的影響，後者會讓區間內的項目
與捲動容器的座標系脫節，兩者都比兩個空 view 難驗。

### 單項高度以常數宣告，並由檢查腳本擋住漂移

推導需要單項高度，而**三處目前都沒有宣告高度** —— 這一節原本寫「三處的項目高度都是固定的」，
**那是錯的，實作時查出來的**：

| 序列 | 高度有宣告嗎 | 實際一致嗎 |
|---|---|---|
| 網格卡片 | 否。`.Card` 的 `height: 100%` 撐的是儲格，而儲格沒有高度 | **否**，見下一個決策 |
| 招式列 | 否，只有 `padding: 3px` | 是 —— 名稱欄有 `text-maxline="1"`，每列恆為一行 |
| 學習者列 | 否，完全沒有高度規則 | 是 —— 同上 |

所以高度不是「拿來用」而是**要先建立**：兩個清單把目前浮現出來的高度明文宣告，卡片走下一個決策。
高度以常數宣告在一處，樣式表用同一個值。**若樣式改了高度而常數沒跟著改，畫面會出現位移或空白** ——
這正是本專案「宣告得下去、不報錯、行為不對」那類失效，所以 `pnpm run check` 要新增一條檢查，
比對常數與樣式表的宣告值。

考慮過並否決：執行期量測項目高度。平台沒有可靠的量測 API，而且量測本身要等第一次繪製，會產生跳動。

### 卡片改為所有列等高，用保留行數而不是截斷

網格的列高**真的會不一致**，而且已經被量過並寫在 `species-card` spec 的 Example 裡：Crabominable 的名稱
換到第二行時，該列兩張卡都是 **209px**，而較短的列是 **193px** —— 差的 16px 正好是一行。

**不能用截斷換取一致**：`species-card` 有一條「Long names wrap rather than truncate」明文寫著名稱超出卡寬時
SHALL 換行、**SHALL NOT** 被裁切或加省略號。**也不能拿最大值當統一高度**：短列會累積誤差，104 列下來
捲動範圍會偏長上千像素，畫面與位移對不上。

採用的做法是**保留行數**：名稱列比照卡片上既有的 `.CardNameAlt`（`min-height: 15px`）與 `.CardForm`
（`min-height: 13px`）的做法，宣告足夠容納最長名稱的最小高度。換行仍然成立 —— 長名稱換到第二行時落在
早已保留好的空間裡，短名稱則把那段空間留白。**這不是新機制，是把卡片上已經用在兩個列的模式補到第三個列。**

代價要明講：**所有卡片都會變成最高那個高度**，畫面比現在鬆、每屏看到的卡片變少。這是換取網格可視窗化的
代價，而網格是三處裡元素最多的一處（約 4000）。

**要保留幾行只能在實機量。** 最長的形態名是「Paldean Form (Combat Breed)」（27 字元），最長的英文種名是
Crabominable（12 字元）—— 但字寬取決於像素字型的實際度量，而 §12.17 已記「web 預覽量不到文字寬度，它用的
是系統字型」。所以保留行數由實機量測決定，不由計算決定。

### 區間只在起始索引改變時才更新

捲動事件的頻率可能很高。每次事件都重新渲染會比不視窗化更慢。推導出的起始索引未變時，不觸發任何更新 ——
以索引而非像素為更新粒度，等於天然的節流，且不需要計時器（§12.14 記過「mount 後等 N 毫秒」在本平台不可靠）。

### 序列改變時區間夾回合法範圍，但不主動捲動

篩選、排序、語系切換都會改變序列長度。區間的起訖必須夾回新的長度，否則會出現空白或越界。
**但不得呼叫任何捲動 API 把畫面移回頂端** —— ROADMAP C 節禁止寫存取捲動位置的程式，而且 Vue 的更新
本來就留著捲動位置。夾住是純推導的一部分（純函式的輸入含項目總數），不是對捲動容器下指令。

### 揭示動畫的錯開改以區間內的序位計算

`DexGrid` 的開機揭示以卡片索引乘 14ms 錯開、上限 26。視窗化之後首屏只掛約 10 張卡，若沿用全域索引，
第一批卡的延遲仍然正確；但捲動後新掛載的卡片會帶著很大的延遲值而看起來像沒有動畫。
**揭示只在開機時播**（`booting` 旗標在查詢結果第一次改變時關閉，§12.14），所以只需確保旗標關閉後
新掛載的卡片不套用任何延遲。

## Implementation Contract

**Behavior**：使用者觀察到的改變只有等待變短。三處的內容、順序、篩選結果、可捲動範圍、捲動位置的保留行為
**都不得改變**。從第一項捲到最後一項全程不得出現空白項、不得出現錯配內容。

**Interface**：新增一個純函式模組，輸入為捲動位移、可視高度、單項高度、每列項目數、項目總數、緩衝屏數，
輸出為起始索引、結束索引、前置佔位高度、後置佔位高度。三個元件共用它，各自只負責接捲動事件與渲染佔位。

**Failure modes**：

- 捲動事件不存在或不帶可用位移 → **停止，不改任何元件**，回報並重新評估（見探針決策）。
- 捲動快於事件頻率 → 邊緣出現空白。緩衝量由探針量到的最大位移間隔決定，不是猜的。
- 單項高度與樣式表不一致 → 由新增的檢查腳本擋下，不倚賴目視。
- 序列變短而區間未夾住 → 由純函式的測試擋下。

**Acceptance criteria**：

1. `pnpm test` 涵蓋區間推導：起訖、佔位高度、序列變短、位移為零、位移超過內容高度、單列與多列，
   以 spec 的 Example 表格逐列驗。
2. `pnpm run check` 新增一條檢查，斷言單項高度常數與樣式表宣告一致，並在不一致時非零退出。
3. iOS 實機：#475 艾路雷朵的詳情等待從 **897ms** 降到 **400ms 以下**（推算約 270ms）。
4. iOS 實機：未篩選網格從第一張捲到第 208 張，**無空白卡、無錯配內容**；最慢 sprite 讀數顯著低於 2327ms。
5. iOS 實機：開一個學習者數量最多的招式（225 筆），從頭捲到尾無空白、無錯配。
6. 篩選與排序的既有測試（66 個）全數通過，且實機上篩選後不留舊卡（`dex-grid` 既有 scenario）。
7. `pnpm run typecheck` 通過。

**Scope boundaries**：

- 在範圍內：新增的推導模組與其測試、三個元件的接線與佔位、新增的高度一致性檢查、
  四份 spec、`design/HANDOFF.md` 與 `ROADMAP.md` 的更新。
- 不在範圍內：Non-Goals 列的每一項。特別是**不要**順手合併數值欄或拿掉包裹用的 view ——
  那是另一個槓桿，混進來會讓驗收條件 3 與 4 分不出是哪一項的效果。

## Risks / Trade-offs

- **捲動事件不帶絕對位移，只有 deltas** → 探針的位移臂先答。累加會漂移，屆時要加「捲到頂歸零」的校正，
  且緩衝量要放大。這是本次最可能改變實作形狀的分岔。
- **捲動事件頻率不足，快速捲動出現空白** → 探針的頻率臂量最大位移間隔，緩衝量據此定而不是猜。
  退路是把緩衝加大到兩屏，代價是首屏元素數變多。
- **單項高度日後被樣式改動而常數沒跟上** → 新增的檢查腳本擋住。這是本次唯一新增的不變式。
- **巢狀捲動下內層事件被外層吞掉** → 招式表與學習者清單都在面板的捲動容器內。§12.19 已實測巢狀同向捲動
  成立，但**事件是否同樣送達內層未測**，由探針在內層容器上一併驗。
- **首屏仍要付約 10 張卡的元素成本** → 這是設計上接受的下限。10 張卡 × 20 元素 × 1.3ms ≈ 260ms，
  與量到的固定成本同級，再往下要靠 Non-Goals 裡那個「減少每項元素數」的槓桿。
- **視窗化讓「捲到哪裡」成為渲染的輸入** → 任何讀錯位移的 bug 都會表現為空白或跳動，而不是報錯。
  驗收條件 4 與 5 要求整條捲完，正是為了讓這類失效無處可躲。

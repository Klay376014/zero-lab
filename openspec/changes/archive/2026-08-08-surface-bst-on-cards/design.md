## Context

以種族值排序時，卡片上沒有任何數字說明順序的依據。`bestBst()` 已存在於資料層並由排序函式使用，所以本次不產生新的資料，只是把已經在決定順序的那個值顯示出來。

現況三點，決定了下面的做法：

- 排序狀態在移植版叫 `stats`，不是設計稿的 `bst`。設計稿的 `state.sort === 'bst'` 這個判斷式不能照抄
- 卡片的屬性列尾端目前只有形態數徽章，它靠自己的 `margin-left: auto` 靠右。要再放一個靠右元素，就不能讓兩者各自宣告 `margin-left: auto` —— 那會把可用空間分配到兩者之間，變成一個貼左一個貼右
- 卡片已經在讀全域的顯示狀態（語系），所以「卡片讀全域」在這個元件上有前例

## Goals / Non-Goals

**Goals**

- 種族值排序時，每張卡片顯示它被排在該位置的依據
- 種族值數字與形態數徽章能同時出現，且順序固定
- 兩者都不存在時，屬性列的高度與現在相同

**Non-Goals**

- 不加 hover 提示、不加無障礙標籤、不改排序邏輯、不動詳情面板、不加第三種排序。理由見 proposal 的 Non-Goals

## Decisions

### 決定一：卡片讀全域 `sortOrder`，不從 `DexGrid` 傳 prop

`SpeciesCard` 直接 `import { sortOrder } from '../state/query.js'`（已 export）。

**替代方案**：由 `DexGrid` 讀取後以 prop 傳入。**不採用的理由**：排序是全畫面一致的顯示狀態，不是某張卡片的屬性。走 prop 會讓 `DexGrid` 純粹為了轉發而持有一個它自己不使用的值，而卡片已經為了語系直接讀全域 —— 同一個元件對兩個同性質的全域狀態用兩種取得方式，比任何一種單獨的做法都難讀。

**這不違反 `species-card` 的「Card takes a species and a form index」需求。** 那條說的是卡片畫哪一個物種的哪一個形態由輸入決定，不是說卡片不得讀取環境顯示狀態 —— 若那樣解讀，現有的語系與模式讀取早就違反了。實作時不要「順手修正」成 prop。

### 決定二：屬性列尾端改為一個容器，用 `margin-left: auto` 而不是 `gap`

新增一個尾端群組 view，`margin-left: auto` 移到它身上，`CardFormCount` 不再自己宣告。群組內順序固定為：種族值數字、形態數徽章。兩者間距用 margin，**不用 `gap`**。

**替代方案**：沿用兩個元素各自 `margin-left: auto`，或用 `gap` 做間距。**不採用的理由**：前者的版面結果是錯的（見 Context）。後者是 `gap` 在這個專案裡從未被使用過 —— `App.css` 全檔沒有一處 `gap` 宣告，而 `margin-left: auto` 有一處且已在裝置上成立。§12 記過這個平台的失敗形狀是「宣告寫得下去、不報錯、行為沒發生」，flex 相關屬性正是已知會被改寫成沒人讀的自訂屬性的那一類。在有已驗證機制可用時引入未驗證的宣告，是拿版面去換一個沒有必要的風險。

**這不是在斷言平台不支援 `gap`** —— 沒有量過。要用它就要先量，那是另一件事。

### 決定三：判斷式寫 `sortOrder === 'stats'`

移植版的排序集合是 `SORT_ORDERS = ['number', 'stats']`。不要引入 `'bst'` 這個字面值，也不要為了貼近設計稿而重新命名排序值 —— 重新命名會動到 `dex-query` spec 與 `QueryBar` 的標籤對應，遠超本次範圍。

## Implementation Contract

**In scope**：`SpeciesCard.vue` 的模板與 script、`App.css` 的卡片屬性列相關規則。

**Out of scope**：`query.ts`（含排序函式與 `SORT_ORDERS`）、`DexGrid.vue`、`i18n.ts`、資料層、詳情面板。

**可觀察的行為**

| 條件 | 屬性列尾端顯示 |
|---|---|
| 排序為種族值、物種有多個形態 | 種族值數字，其後為形態數徽章 |
| 排序為種族值、物種只有一個形態 | 只有種族值數字 |
| 排序為編號、物種有多個形態 | 只有形態數徽章（與現況相同） |
| 排序為編號、物種只有一個形態 | 兩者皆無（與現況相同） |

**數值契約**：顯示的數字為 `bestBst(species)`，即該物種**所有形態**中最高的種族值總和 —— 不是當前顯示形態的種族值。這與排序用的值是同一個函式的同一個回傳值，兩者必須一致，否則畫面會顯示一個無法解釋所在位置的數字。

**驗收條件**

1. 切到種族值排序，第一張卡片的數字**大於或等於**第二張卡片的數字，且沿著整個網格單調不遞增
2. 妙蛙花（#0003，2 個形態）在種族值排序時同時顯示數字與形態數徽章 `2`，數字在左、徽章在右
3. 百變怪（#0132，單形態、無 Mega）在種族值排序時只顯示數字，切回編號排序後該列尾端為空
4. 切換排序時卡片不重新掛載 —— 圖片不重新載入、不閃爍
5. `pnpm run check` 與 `npm exec tsc -- --noEmit -p src/tsconfig.json` 均為 exit 0
6. 裝置驗收：iOS 實機，種族值排序下捲過數列，數字與徽章在同一水平線上且不與屬性縮寫重疊

**失敗模式**：若尾端群組的 `margin-left: auto` 沒有生效，症狀是數字與徽章緊貼在屬性縮寫右側而不是卡片右緣。這不會報錯，要用目視確認。

## Risks / Trade-offs

- **屬性列變窄** → 雙屬性（兩個字符加兩組三字縮寫）加上數字加上徽章，是最壞情況。驗收條件 6 就是為了這個。若真的擠不下，退路是讓屬性列在該情況換行，而不是縮小數字字級
- **數字是「最佳形態」而非「當前形態」，可能造成誤讀** → 這是設計稿的既有語意，且與排序依據一致。改成當前形態會讓排序與顯示不一致，那更糟。設計稿用 hover 提示解釋這件事，移植版沒有 hover 也不補 —— 接受這個取捨，並記在 spec 的 scenario 裡讓它是被要求的狀態而非疏漏
- **`sortOrder` 從 query 模組流入卡片，增加一條耦合** → 已在決定一說明。風險是日後有人把它「修正」成 prop，所以該決定寫明了不要這樣做

## Migration Plan

無資料遷移、無設定變更。單一 commit 即可，回退即還原兩個檔案。

## Open Questions

無。三個決定都已定案，平台問題只剩驗收條件 6 的目視確認，那屬於實作後的裝置驗收而不是開工前的未知。

# LANGUAGE — 這個專案的共用詞彙

`/spectra-discuss` 在每次討論開始前讀這份檔案，用來在 artifact 裡挑正規用語、並在討論偏離時
把它當成「詞彙漂移」點出來。

**這份檔案管什麼**：同一個概念有多種叫法、而混用會讓 artifact 讀起來像在講兩件事的詞。
**這份檔案不管什麼**：只出現一次的名詞、程式碼裡的識別字、以及 spec 的規範語彙
（SHALL／MUST）—— `openspec/specs/` 一律英文，那是格式規定不是詞彙選擇。

每一筆的欄位：

- **definition** —— 這個詞指什麼
- **avoid** —— 指同一件事、但不該在 artifact 裡出現的說法
- **why** —— 為什麼挑這個而不是那個

---

## 本系加成

| | |
|---|---|
| **definition** | 招式的屬性與使用它的形態的屬性之一相同，且該招式不是變化招式時，攻擊獲得的加成。判定依**顯示中的形態**，不是物種 |
| **avoid** | 「屬修」、「STAB」、「同屬性加成」 |
| **why** | 「本系加成」是 artifact 通篇的用語。**唯一的例外是 UI 上那顆控制項，標籤寫「★ 屬修」** —— 那是為了塞進晶片寬度而做的取捨，不是換了一個概念。`src/data/i18n.ts` 的 `mvStab` 鍵旁邊已註明這件事。英文側對應的 UI 標籤是 `★ STAB`，spec 內文一律寫 same-type attack bonus |

## 學習者清單

| | |
|---|---|
| **definition** | 由一個招式反查、列出會該招式的物種，並可從中切換詳情的那一層畫面 |
| **avoid** | 「反向索引」（指的是資料層的推導，不是畫面）、「相關寶可夢」（沒說出關係是什麼） |
| **why** | 討論這個功能時同時出現過三種叫法，其中「反向索引」與「學習者清單」指的其實是**不同的層**：前者是 `src/data/dex.ts` 裡的推導，後者是使用者看到的東西。兩者混用會讓「清單要不要記憶化」這種句子無法判斷在問哪一層。規則是：講資料層的推導寫「反向索引」，講畫面寫「學習者清單」，而**功能整體**用「學習者清單」。⚠️ **2026-08-11：「招式詳情」已從 `avoid` 移出。** 這一筆原本把它列為要避免的說法，理由是「清單不描述招式本身」—— 那在當時成立，因為沒有任何畫面在描述招式本身。招式分頁把那個畫面做出來之後，「招式詳情」成為[[招式詳情]]的正名，繼續留在這裡會擋到正確用法 |

## 形態

| | |
|---|---|
| **definition** | 一個物種底下的一種外觀與數值組合，含基本形態、地區形態、MEGA 與其他形態四類 |
| **avoid** | 「型態」、「樣子」、「變體」 |
| **why** | 資料集的 `Form` 與 UI 的形態切換器都用這個詞，`i18n.ts` 的 `dForm`／`baseForm` 亦然。「樣子」是遊戲官方譯名在特定形態上的用法（例如「阿羅拉的樣子」），**那是那個形態的名字，不是這個類別的名字** —— 講類別寫「形態」，引用某個具體形態時照抄它的官方名稱 |

## 屬性

| | |
|---|---|
| **definition** | 十八種屬性之一，套用在形態上或招式上 |
| **avoid** | 「型別」、「類型」 |
| **why** | 「型別」在這個專案裡已經被 TypeScript 的 type 佔走了，`src/data/types.ts` 同時裝著兩種意思的東西。artifact 講遊戲概念一律寫「屬性」，講程式語言概念寫「型別」。i18n 的 `type`／`dTypes` 鍵值都是「屬性」 |

## 簡稱

| | |
|---|---|
| **definition** | 招式 flag 顯示在[[招式詳情]]晶片上的那個名詞（「接觸」、「守住」、`Contact`、`Protect`），中英各一 |
| **avoid** | 「標籤」、「flag 名稱」 |
| **why** | 2026-08-11 決定顯示範圍的那次討論裡，同一個東西出現了三種叫法：`ROADMAP.md` A11 的欄位名寫「簡稱」，討論過程寫「標籤」，`move-detail` spec 寫 "flag label"。**「標籤」不行的理由是實際會混淆** —— 這個 app 的 UI 裡「標籤」已經指欄位名（`i18n.ts` 的 `md*` 鍵、`DetailAttrKey` 那一類），而簡稱是值不是鍵，兩者在同一個句子裡出現的頻率很高（「標籤旁邊要不要放簡稱」）。**英文側 spec 沿用 "flag label"**，因為那裡沒有這個撞名：欄位名在英文 spec 裡叫 "field label"。要區分兩層時，flag 的**編號**與上游的 **identifier** 都不是簡稱 —— A11 定的綁定是 `編號 → identifier → 簡稱` 三段，句子講的是哪一段必須寫清楚。**承載這些簡稱的那一列叫「性質」**（`i18n.ts` 的 `mdFlags`，英文標籤 `Flags`）—— 列名與列裡的值是兩件事，「性質有幾個」與「簡稱有幾個」問的不是同一件事 |

## 佔位磚

| | |
|---|---|
| **definition** | 蓋在 sprite 上、載入成功前一直存在的那塊方形替代物，內容是該形態第一個屬性的字符。卡片與詳情面板各有一個 |
| **avoid** | 「替代圖塊」、「屬性字符佔位」、「佔位圖」、單獨用的「佔位」 |
| **why** | 同一個東西在文件裡有四個名字（`HANDOFF.md` §12.6 寫「替代圖塊」、§12.16 寫「屬性字符佔位」、§3 寫「佔位圖」，spec 寫 "glyph tile"），而**單獨用「佔位」會跟 §12.18 的搜尋框佔位字撞名** —— 那是 placeholder text，完全是另一回事。這個區分在效能主題上會實際造成誤讀：未篩選的網格裡 543 個字符元素有 **208 個**是佔位磚（§12.24），句子講的是哪一個必須一眼看得出來。英文側 spec 沿用既有的 "glyph tile"／"placeholder tile"，不因這一筆改寫 |

## 招式詳情

| | |
|---|---|
| **definition** | 描述一個招式本身的那一層畫面：屬性、傷害類別、威力、命中、PP、說明文字，以及進入[[學習者清單]]的入口 |
| **avoid** | 「招式頁」（會跟[[分頁]]裡的招式分頁撞名）、「招式資訊」、「招式卡」 |
| **why** | 這個詞在 2026-08-11 之前是[[學習者清單]]那一筆的 `avoid` 項，因為當時沒有任何畫面在描述招式本身，用它指學習者清單是錯的。招式分頁把這個畫面做出來之後它才有指涉對象。**「招式頁」不行的理由是實際會混淆**：招式分頁是[[分頁]]那一層（並列、互斥），招式詳情是[[層]]（疊上去、可回捲），而兩者在同一個句子裡出現的頻率很高 —— 「從招式頁進招式頁」是這個功能真實存在的路徑 |

## 分頁

| | |
|---|---|
| **definition** | 應用最上層的兩個並列內容區（圖鑑、招式），彼此互斥，同時只有一個顯示。切換不改變任何[[層]]的內容 |
| **avoid** | 「切頁」、「頁籤」、「tab」、「頁面」 |
| **why** | 討論過程裡「分頁」「切頁」「頁籤」三種都出現過，其中「切頁」指的其實是**動作**而不是東西，混用會讓「切頁的入口」這種詞組讀不出是在講控制項還是講轉場。定「分頁」為名詞、「切換分頁」為動作。**「頁面」不能用**，因為它跟[[層]]同樣可以被理解成「一個滿版的畫面」，而這兩者的堆疊規則完全不同 |

## 層

| | |
|---|---|
| **definition** | 疊在[[分頁]]之上、覆蓋內容區的畫面單位，共三種：物種詳情、[[招式詳情]]、[[學習者清單]]。堆疊規則是**每種層最多一個實例，開啟一個已在堆疊裡的層是回捲到它並換掉內容** |
| **avoid** | 「dialog」、「彈窗」、「對話框」、「畫面」 |
| **why** | 「dialog」是討論這個功能時最自然冒出來的字（「太多層 dialog」），但它在這個 app 裡指涉不準：這三種東西都不是模態對話框，沒有確認／取消語義，而且**其中兩種自己帶捲動容器** —— 叫它 dialog 會讓人以為 `species-detail` 那條「面板恰好一個捲動容器」的限制不適用。更關鍵的是回捲規則要寫成 SHALL，而那句話裡「層」必須是一個有明確成員數（三個）的封閉集合，「dialog」沒有這個性質。英文側 spec 沿用既有的 "layer"／"overlay"，`move-learners` spec 已經在用 |

## 維護方式

- 一個概念在討論裡出現第二種叫法、而兩種都說得通時，才需要進來。**只有一種叫法的詞不必登錄**
- `avoid` 欄不是禁令，是預設值。既有程式碼與資料集欄位名不因為這份檔案改名 ——
  重新命名要走自己的 change
- 一筆的 `why` 寫不出來，通常代表那不是詞彙問題而是概念還沒想清楚
